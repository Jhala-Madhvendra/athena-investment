# Advanced Scenario Analysis — Product Design

## 1. Why basic scenarios are insufficient

A single-factor scenario ("what if Technology drops 20%") answers a narrow question well, but real stress events rarely arrive as a single clean shock — a broad market decline, a sector-specific selloff, and a company-specific event frequently compound. Worse: Sprint 15's commit message claimed a basic scenario engine already existed, but inspection before writing any Sprint 16 code (`git show --stat` on that commit) found no scenario code anywhere in the repository — only transaction-ledger and historical-reconstruction work had actually shipped. Sprint 16 had to deliver the single-factor engine the brief assumed existed *and* the multi-factor capability it asked for on top of it.

## 2. Why users need multi-factor scenarios

A realistic stress question is almost never "just Technology" — it's "Market down broadly, Technology down more than the market, and this one specific holding down even further because of company-specific news." Multi-factor scenarios let a user compose that full picture in one request and see the combined, non-double-counted result, rather than manually estimating how several single-factor scenarios might interact.

## 3. Why Bear/Base/Bull scenarios are useful

They're a familiar, low-friction way to communicate a range without requiring a full probability distribution — most investors already reason in these terms. Comparing Bear against Bull surfaces how directionally sensitive a portfolio is, independent of which scenario a reader personally thinks is more likely. Athena reuses the same three-scenario convention DCF valuation already established (Sprint 6/7), applied to portfolio-level shocks instead of valuation assumptions.

## 4. Why assumptions must be transparent

Every number this feature produces is conditional on a specific, stated hypothesis — if that hypothesis is buried or unclear, the number reads as more authoritative than it is. Every scenario response carries a visible `assumptions` block (rules, portfolio value used, beta used, methodology notes, data timestamp) for the same reason Sprint 14 made its own Assumptions panel always-visible rather than a tooltip: a reader who doesn't know a number is an estimate under specific stated conditions will treat it as a stronger claim than Athena is actually making.

## 5. Why scenarios are not forecasts

This is the sprint's single non-negotiable framing constraint, stated in the brief itself: Athena must never imply "this will happen," only "if these assumptions occur, the modeled impact is X." Every scenario result, every preset, and every piece of UI copy is worded conditionally — "Hypothetical - not a forecast" appears directly in the result header, not just in documentation. The reason is trust: a tool that quietly drifts from "here's a hypothetical" to "here's what will happen" would be making an investment prediction it has no basis to make, and users would reasonably lose confidence the moment that framing slipped even once.

## 6. Why users should control scenario assumptions

The alternative — Athena deciding what shock values are "realistic" — would mean the tool is making an implicit forecast on the user's behalf, dressed up as a neutral default. Historical data is shown as separate context specifically so it can inform the user's own judgment without ever substituting for it (`research/finance/HistoricalStressContext.md`): a user's "-15%" is always applied as "-15%," never quietly replaced by a data-derived alternative.

## 7. Why AI should not generate the shocks

Same reasoning as Section 5 and 6, applied to a specific failure mode: an AI suggesting "Technology should probably see a -25% shock" is functionally a forecast, generated by a system with no principled basis for it, laundered through a UI element that looks like a neutral tool. The sprint brief states this directly ("do not ask an LLM what shock a sector should receive"), and `research/engineering/GroundedScenarioExplanation.md` documents the boundary precisely: AI, if ever added, may only restate already-computed numbers, never generate new ones.

## 8. Why scenario history is deferred

No `Scenario` collection, no saved-scenario templates, no scenario run history — scenarios are computed and returned in a single request, then discarded. This keeps the feature's infrastructure footprint matched to what's actually validated: whether users find running and comparing hypothetical scenarios useful at all, before investing in persistence, sharing, or scheduled re-runs of something whose product-market fit within Athena isn't yet established. If usage data later shows users repeatedly reconstructing the same scenario by hand, that's the concrete signal that would justify building persistence — not an assumption made in advance.

## 9. Why scenario results should remain neutral

Athena describes modeled consequences ("Technology represents 52% of current portfolio value; a 20% Technology shock produces an estimated 10.4% portfolio decline under the scenario's assumptions") and stops there — never "you should reduce Technology exposure," never a BUY/SELL/HOLD/REDUCE/INCREASE label, never a "best"/"most dangerous" ranking in scenario comparison. Athena has no visibility into a user's risk tolerance, time horizon, tax situation, or goals outside the app — the same reasoning Sprint 14's `PortfolioRiskProductDesign.md` already established for why portfolio optimization is out of scope. Describing a portfolio's modeled behavior under stated conditions is a well-scoped problem Athena can answer correctly with the data it has; prescribing what to do about it is a fundamentally different, much riskier one.

## 10. How scenario analysis complements Portfolio Analytics

Sprint 14 answers "how has this portfolio actually behaved" (volatility, Sharpe, historical beta, historical drawdown) — backward-looking, and structurally limited to what's present in the historical sample. Scenario analysis answers "how would this portfolio behave under a condition that hasn't necessarily happened yet" — forward-looking and hypothetical, filling exactly the gap backward-looking risk metrics can't: rare, severe events are by definition under-represented in any historical window. The two are deliberately kept visually and structurally separate on the page (Historical Context is its own card within the scenario result, distinct from the scenario numbers themselves) so a reader always knows which kind of claim they're looking at.

## 11. How this can eventually support portfolio monitoring

A saved, named scenario re-run automatically as market conditions change (e.g., "alert me if my portfolio's live composition would now lose more than 15% under my saved Bear Case") is a natural extension once scenario persistence exists (Section 8) — bridging this feature with Sprint 11's Intelligent Alerts infrastructure. Deliberately not built this sprint: it depends on scenario persistence existing first, and validating that manually-run scenarios are useful on their own is the right precondition before automating them.

## 12. What user research should validate

Whether users actually understand the precedence model without reading documentation — "if I set a sector shock AND an asset shock for the same holding, only one applies" is a specific, non-obvious mechanic that the UI surfaces via a visible rule-chip and an explanatory footnote, but hasn't been validated with real users. Whether the weight-vs-contribution distinction (`research/finance/ScenarioAttribution.md`) is understood without misreading Contribution to Impact as portfolio weight — the two-column table plus an explicit footnote is the current mitigation, unverified with real users. Whether the "Hypothetical - not a forecast" framing is actually retained by users after repeated use, or whether familiarity erodes the caveat's effect over time — the same open question `PortfolioRiskProductDesign.md` raised for Sharpe Ratio/Beta jargon comprehension.

## Potential product metrics (not implemented this sprint)

Scenario runs, preset usage vs. custom scenario usage, scenario comparison usage, sensitivity analysis usage, repeat scenario analysis per user. None of these are implemented as analytics instrumentation in Sprint 16 — per this document's own "don't build for a metric without a validated need" reasoning (Section 8), and because no analytics/telemetry layer exists elsewhere in Athena's frontend to hang them on.
