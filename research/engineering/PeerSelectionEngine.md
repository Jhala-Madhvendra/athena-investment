# Engineering Concept: The Peer Selection Engine

## What it is

`backend/valuation/comps/comps.peerSelector.js` (candidate discovery, `getAvailablePeerCandidates()`) and `comps.validator.js` (structural validation, `validatePeers()`) together form Sprint 7's peer-selection layer: one surfaces *candidates* a user might add as a peer, the other enforces the mechanical rules once a peer list has been chosen. Neither one decides which companies actually *are* comparable — that judgment is left to the user, by design (see `research/finance/PeerSelection.md`).

## Why we use it

Peer selection has two genuinely different failure modes that call for different code: a **data problem** (does Athena even have a company matching what the user typed, and does it have financial statements) and a **judgment problem** (is this company economically comparable to the target). Athena's architecture solves the first with code and deliberately does not attempt to solve the second with code — conflating the two into one "smart" peer-suggestion function would blur that line and risk presenting a data-availability list as if it were a comparability verdict.

## Alternatives considered

- **An automatic similarity-scoring algorithm** (weight sector match, revenue-scale proximity, market-cap proximity, etc. into a single "comparability score" and rank candidates by it). Rejected for this version — not because it's technically infeasible, but because Athena's current data model (sector/industry strings, a point-in-time market cap, imported revenue) is too coarse to make that score trustworthy, and a wrong automatic ranking, presented with algorithmic authority, is a worse outcome than an unranked candidate list a human has to evaluate (see `research/product/ComparableCompaniesProductDesign.md`).
- **Calling the live market-data provider for every candidate** to show a live market cap in the browsing list. Rejected — browsing candidates is a lightweight, frequent, exploratory action; hitting Yahoo once per candidate row would make the list slow and would burn API calls for data (`Company.marketCap`, snapshotted at import time) Athena already has stored.
- **Auto-importing a peer's financial statements the moment it's added to the list.** Rejected — importing financial statements is a deliberate, explicit action everywhere else in the app (`POST /api/financials/import/:ticker`); silently triggering it as a side effect of peer selection would be a surprising, hidden network call, and if the import failed, it would be unclear to the user why.

## Trade-offs

**For the "candidates only, not recommendations" approach:** the `limitation` string returned by `getAvailablePeerCandidates()` is not decorative — it is the load-bearing explanation for why this endpoint's output looks the way it does, and every response carries it so the frontend can never render the candidate list without that context. Peer-comparability judgment stays where it belongs (with a human who can weigh business model, growth, and geography — factors Athena doesn't currently model at all).

**Against it:** the feature is less "magical" out of the box than a ranked recommendation list would be — a first-time user has to do real work (search, evaluate, select) rather than accept a default. This is an intentional trade of convenience for trustworthiness; see `PeerSelection.md`'s Section 10 for what a genuine future auto-recommendation engine would need to earn back that convenience responsibly.

## How Athena implements it

`getAvailablePeerCandidates(targetTicker, searchQuery?)` queries the `Company` and `FinancialStatement` Mongoose models **directly** (not through a Yahoo Finance client — there's nothing to duplicate here, this is a read of Athena's own already-imported data), excludes the target, optionally filters by a case-insensitive name/ticker regex, caps results at `CANDIDATE_LIMIT` (25), and attaches each candidate's latest reported revenue *only if* financial statements have actually been imported for it — `hasFinancialStatements: false` and `revenue: null` otherwise, never a fabricated figure. Once the user has picked a list, `comps.validator.js`'s `validatePeers(targetTicker, rawPeers)` runs before any data is fetched: it normalizes casing, silently removes the target if included as its own peer and duplicate tickers (reporting both as non-fatal `notes`, not `errors`, since the request can still proceed with a cleaned list), rejects invalidly-formatted tickers outright, and requires at least `MIN_PEERS` (2) remain. Only *after* that structural gate does `comps.service.js` attempt to actually fetch each peer's data — and a peer that structurally validated but turns out to have no imported statements is excluded there, not here, with its own stated reason (see `DynamicValuationCalculation.md`).

## Interview questions

1. *"Why are peer-ticker validation and peer-data-availability checking two separate functions in two different files, instead of one combined 'validate this peer list' function?"* — They run at genuinely different times against genuinely different failure modes: ticker format/dedup/target-exclusion can be checked instantly with no I/O (`comps.validator.js`), while data availability can only be known after attempting a database fetch per ticker (`comps.service.js`). Fusing them would mean either doing unnecessary I/O for a structurally-invalid request, or losing the fast-fail behavior a malformed ticker deserves.
2. *"What would you need to add to `comps.peerSelector.js` to make it a genuine recommendation engine, and what's the risk of doing that today?"* — At minimum, a finer-grained business-model classification and some notion of growth/margin trajectory (see `PeerSelection.md`'s Section 10) — today's inputs (sector/industry strings, market cap, revenue) can rank candidates by superficial similarity but can't distinguish "same sector, genuinely comparable business" from "same sector, entirely different economics." Shipping a ranked list on today's data would risk the exact sector-only-filtering mistake `PeerSelection.md` opens with, just automated instead of made by a human.
3. *"Why does peer candidate browsing never call the live market-data provider, when the actual Comps calculation does?"* — Different jobs: browsing candidates is exploratory and needs to be fast and cheap, drawing only on data Athena already has stored; the actual calculation needs today's live price and market cap to be meaningful at all, so it's worth the live fetch there. Using the same live-fetch pattern for both would make browsing 25 candidates cost 25 live API calls for no benefit to the browsing experience itself.
