# Alert Lifecycle

## What it is

The states an `Alert` document moves through after creation — unread → read (and independently) → dismissed — plus how long it's kept before being removed entirely.

## Why it is needed

An alert that can only ever be "new" or "gone" forces a false choice: either the Alert Center accumulates forever (every alert ever generated, unread and read alike, indistinguishable), or dismissing loses information a user might want to reference later ("wait, what was that alert about AAPL last week?"). Two independent booleans (`isRead`, `isDismissed`) plus a retention window solve both without conflating "I've seen this" with "I'm done with this."

## Alternatives considered

- **A single `status` enum (`unread`/`read`/`dismissed`).** Considered, but rejected in favor of two independent booleans — read and dismissed aren't mutually exclusive states in the way an enum implies (an alert can be read *and later* dismissed, or dismissed *while still unread* if a user clears their whole feed without expanding each card). Two booleans model that correctly; an enum would need a `readAndDismissed` case that's really just two facts pretending to be one.
- **Hard-delete on dismiss.** Rejected — the sprint brief explicitly says not to delete on dismiss, and it matches how every other "clear this notification" UI a user is likely to have encountered actually behaves: dismissing declutters the active view, it doesn't erase history.
- **Indefinite retention (never delete anything).** Rejected — an alert about a financial-statement change from a year ago has essentially zero decision value once newer statements have superseded it, and indefinite retention only grows a collection with no corresponding benefit. See the Retention section below.

## Trade-offs

- **Pro (two booleans over an enum):** every combination is representable without a synthetic composite state, and each transition (`markAsRead`, `dismissAlert`) is a simple, independent update — no state-machine validation logic needed to reject an "invalid" transition, because there isn't one.
- **Pro (TTL over manual archival):** a Mongo TTL index (`expireAfterSeconds` on `createdAt`) needs zero application code to enforce — no cron job, no batch-delete script, no risk of the cleanup job itself silently failing. It's the same mechanism (and reasoning) `NewsArticle`'s retention already uses.
- **Con (TTL over manual archival):** no "restore" path — once an alert ages out, it's genuinely gone, not soft-deleted. Accepted because the sprint brief explicitly asks not to over-engineer archival, and a 90-day-old alert's practical value (verifying a claim, not acting on stale data) doesn't justify building a restore feature for it.

## How Athena implements it

`alert.model.js`: `isRead` and `isDismissed`, both `Boolean, default: false`. `PATCH /api/alerts/:id/read` and `PATCH /api/alerts/:id/dismiss` (`alert.controller.js` → `alert.service.js` → `alert.repository.js`) each update exactly one field, scoped `{_id, userId}` together so a guessed id belonging to another user matches nothing. `GET /api/alerts` always excludes `isDismissed: true` from its results (`alert.repository.js`'s `buildListQuery`) — dismissed alerts are preserved in the database, just no longer surfaced in the default feed; there is currently no "view dismissed" endpoint, since nothing in the sprint brief's explicit API list calls for one. Retention: a TTL index on `createdAt` with `expireAfterSeconds` derived from `env.alertRetentionDays` (default 90) — matching the exact precedent and reasoning `NewsArticle`'s retention already established in Sprint 10 (`research/engineering/NewsCaching.md`).

## Post-sprint fix: the sidebar badge going stale across a read/dismiss transition

The server-side lifecycle above was correct from Sprint 11 onward, but a real bug surfaced later in the *frontend's* reflection of it: `Sidebar.jsx`'s unread-count badge (`frontend/src/components/shell/Sidebar.jsx`) fetched `GET /api/alerts/unread-count` exactly once, on mount, and never again. Because `Sidebar` is mounted once in `App.jsx` and never remounts as the user navigates between routes (it's a persistent rail, not a per-route component), marking an alert read or dismissed on the Alerts page had no way to reach it — the two are sibling components with no shared parent state, and no lifecycle event connects them. The badge was correct at the moment the app loaded and then simply drifted from reality for the rest of the session.

The fix is a minimal pub/sub module, `frontend/src/lib/alertsBadge.js` (`notifyAlertsChanged()` / `subscribeToAlertsChanged()`), not a general state-management library. `Alerts.jsx` calls `notifyAlertsChanged()` after any server-confirmed action that could change the unread count (marking read, dismissing, or "Check for New Alerts" creating new ones); `Sidebar.jsx` subscribes on mount and re-fetches the real count from `/api/alerts/unread-count` — never a locally-computed delta — whenever notified, unsubscribing on unmount. This keeps the server (`alert.repository.js`'s `countUnread`) as the single source of truth for the number itself; the pub/sub only carries a "something changed, go check" signal, never the count itself, so the two components can never disagree about what the count *is*, only about how quickly each learns it changed.

## Post-sprint fix #2: PATCH was never CORS-allowed, so read/dismiss silently never reached the server at all

The pub/sub fix above was necessary but, it turned out, not sufficient - a user reported the read feature still "wasn't working" even after it shipped. Manually reproducing the flow in a real browser (not a unit test - see below for why that distinction mattered) surfaced the actual root cause, one step further back than the badge: `PATCH /api/alerts/:id/read` and `/:id/dismiss` were never reaching Express at all. `server.js`'s CORS configuration explicitly allowlists HTTP methods (`methods: [...]`, now `config/corsOptions.js`), and `PATCH` was never added to it when Sprint 11 introduced these two routes. A real browser preflights any non-"simple" request (PATCH always is) with an `OPTIONS` request first, and refuses to send the actual `PATCH` at all if the method isn't in the preflight response's `Access-Control-Allow-Methods` header - so every click silently failed in `Alerts.jsx`'s `catch { /* best-effort */ }`, the optimistic UI update made the card *look* read, and the badge fix above had nothing to notify about, because the `await fetchJson(...)` it depends on never resolved successfully in the first place.

**Why no test caught this for multiple sprints:** every existing test for this flow (`Alerts.test.jsx`, `alert.routes.test.js`) mocks `fetch` directly - a mock has no concept of a CORS preflight, so it can't fail the way a real browser does. This is a structural blind spot of testing frontend code against a mocked network layer: the mock proves the component *calls fetch correctly*, never that the *browser would actually deliver the request*. The bug was only found by launching the real backend and frontend dev servers and driving an actual Chromium instance through the flow (Playwright), watching the real network tab - the CORS error was immediately visible there and invisible everywhere else.

**The fix:** add `"PATCH"` to `config/corsOptions.js`'s `ALLOWED_CORS_METHODS`. **The regression guard:** `backend/__tests__/corsMethods.test.js` scans every `*.routes.js` file's actually-registered Express methods (via each router's own `.stack`, not a hand-maintained list) and asserts every one of them appears in `ALLOWED_CORS_METHODS` - so the next route added with a method nobody thought to CORS-allow fails a fast, specific unit test (`"alerts/alert.routes.js: PATCH"` in the actual failure output) instead of silently breaking in a browser for an unknown number of sprints. Verified the test would have caught the original bug by temporarily reverting the fix and re-running it before restoring - it failed with exactly that diagnostic.

## Interview questions (continued)

5. *"Why didn't Sidebar's badge just re-fetch on every route change, instead of adding a pub/sub module?"* — Because most route changes have nothing to do with alerts — re-fetching on every navigation would mean far more requests than necessary and would still miss the actual moment of change if a user marks something read without navigating away from the Alerts page at all (the bug this fixed happens on the *same* page, no navigation involved). A targeted "notify on the specific actions that change the count" signal is both more accurate and cheaper than a blunt "re-fetch on any navigation" heuristic.
6. *"Why does the pub/sub only carry a 'something changed' signal instead of the new count itself?"* — So there's exactly one source of truth for the number - the server. If `Alerts.jsx` computed and broadcast a new count itself, that count could drift from the server's real value (e.g., if the PATCH request that triggered it actually failed after the broadcast already fired) - Sidebar re-fetching the authoritative count every time it's notified means it can never be wrong for longer than one round trip, regardless of what the notifying component's own local state thinks happened. This turned out to matter concretely: point 6's own scenario (the PATCH silently failing) is exactly what the CORS bug below caused for several sprints, and the design already handled it correctly - the badge simply never learned about a change that never actually happened.
7. *"A component's unit tests all pass, but a real user says the feature doesn't work. What class of bug does that combination point toward?"* — Something the test's mocks can't represent - most commonly, real network/browser behavior a mocked `fetch` never exercises (CORS, cookies, redirects, actual HTTP status semantics) or real timing (races, debounce, a second render). The alerts PATCH-blocked-by-CORS bug is a concrete instance: `Alerts.test.jsx` mocked `fetchJson` directly and therefore could never fail the way a real preflight fails - the test was validating "does the component call the right function with the right arguments," not "does a real browser successfully deliver this request," and those are genuinely different guarantees.
8. *"Why is `corsMethods.test.js` a stronger regression guard than just adding a comment reminding future developers to update the CORS methods list?"* — A comment relies on someone remembering to read it at exactly the right moment (when adding a new route with a method not yet CORS-allowed); a test fails the build automatically and immediately, with the specific file and method that's uncovered, regardless of whether anyone thought to check. It also doesn't need to know about "the alerts case" specifically - it would catch the same class of mistake for any future domain that introduces a new HTTP method, verb-agnostic and route-file-agnostic by construction.

## Interview questions

1. *"Why two booleans instead of a status enum?"* — Because read and dismissed genuinely are independent facts about an alert, not mutually exclusive states — an enum would need an artificial composite value (or would have to pick one fact to lose) for the case where both are true, which is a real, reachable case (a user reads an alert, then later clears it from their feed).
2. *"Why does dismissing not delete the alert?"* — Because "I don't need to see this in my active feed anymore" and "this never happened" are different intents, and the sprint brief is explicit that dismiss shouldn't destroy history a user might want to verify or reference later.
3. *"Why 90 days for retention, and why a TTL index instead of a cleanup job?"* — 90 days matches the same reasoning `NewsArticle` already uses: an alert's decision-relevance decays fast (newer financials/prices supersede it), and a TTL index enforces that at the database layer with no application code, no scheduled job to fail silently, and no batch-delete script to get the query wrong on.
4. *"What happens to a user's unread count when an alert both ages out via TTL and was never read?"* — It simply stops being counted the moment Mongo expires the document — `countUnread`'s query (`{userId, isRead: false, isDismissed: false}`) only ever sees documents that still exist, so TTL expiry and the read/dismiss lifecycle compose without any special-case handling needed between them.
