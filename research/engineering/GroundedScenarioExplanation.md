# Grounded Scenario Explanation

## Definition

The design for an optional AI layer that turns a scenario's structured result into a plain-English explanation. Designed as a *deferred* integration point in Sprint 16, and implemented exactly as specified in Sprint 17: `POST /api/portfolio/scenarios/explain` (`portfolio.scenario.explanation.{validator,promptBuilder,service,responseValidator}.js`, wired into `portfolio.scenario.controller.js`/`portfolio.scenario.routes.js`). Every constraint below was written down *before* implementation began, specifically so no time-pressured shortcut could quietly weaken it once building started — the implementation was checked against this document, not the other way around.

## Why deterministic scenario calculations are necessary

Every number a scenario response contains — portfolio/holding/sector values, absolute and percentage change, attribution — comes from `portfolio.scenario.resolver.js` and `portfolio.scenario.calculator.js`, pure functions with no LLM involvement anywhere in the call path. This remains true with the explanation layer implemented: `/explain` never recomputes a scenario. It only accepts a result the caller already received from `/run` or `/compare`, validates its shape, and asks an LLM to describe it in prose. An LLM is a plausible-text generator, not a verified arithmetic engine, and letting it compute or adjust a dollar figure would mean the number displayed to a user is no longer traceable to a specific, testable formula.

## How structured scenario results are passed to AI

`portfolio.scenario.explanation.validator.js`'s `validateExplanationRequest` is the enforcement mechanism, not just documentation of intent: it builds `normalized` as an explicit allow-list copied out of the request body — `scenario.{name,rules}`, `currentPortfolioValueUSD`, `scenarioPortfolioValueUSD`, `absoluteChangeUSD`, `percentageChange`, `holdingImpact`, `sectorImpact`, `historicalContext`, `assumptions` — the same shape a human reader already sees on the Scenario Analysis page. Any other key on the request body (e.g. a caller attaching an unrelated instruction) is silently dropped before the prompt is ever built, exactly as this document specified when it was still a "would be" rather than an "is." No raw market data, no unstructured text, no separate data-fetching step exists for the AI to draw from.

## Why AI does not generate financial assumptions

A scenario's shock values are the user's stated hypothesis — this stays exactly what the user entered, never silently adjusted by anything (including historical data, per `research/finance/HistoricalStressContext.md`, and including an LLM). `/explain`'s only inputs are an already-computed result and its own system prompt (`portfolio.scenario.explanation.promptBuilder.js`), which explicitly forbids the model from proposing a shock value, a probability, or a recommendation. There is no code path from the explanation layer back into `resolver.js` or `calculator.js` — the explanation is a dead end, read-only with respect to the scenario engine.

## Why the response is a JSON envelope, not plain prose

The first implementation asked the model for plain prose text with no JSON. This broke against a fact discovered mid-sprint: two of Athena's three configured LLM providers force JSON output at the HTTP transport level, unconditionally, for every call through `llmProvider.generateReport()` — `openaiClient.js` sets `response_format: { type: "json_object" }` and `geminiClient.js` sets `generationConfig.responseMimeType: "application/json"`, both added for Sprint 8's JSON research report and shared by every caller since `generateReport` is the LLM provider interface's only method. Asking those providers for "plain prose only" doesn't turn the constraint off — it just leaves the model resolving a contradiction on its own, which in practice produced a JSON object whose value was itself an escaped JSON string (`"{\"explanation\": \"...\"}"`), visible verbatim to a user before this was caught. The fix embraces the constraint instead of fighting it: the prompt now asks for `{"explanation": string}`, and `portfolio.scenario.explanation.responseParser.js` (mirroring `ai.responseParser.js`'s existing recovery pattern) extracts the string — including unwrapping one extra layer of accidental double-encoding, the specific failure mode observed. This is provider-agnostic: Anthropic, which has no forced-JSON transport option, satisfies the same envelope shape from prompt instruction alone.

## How hallucination risk is controlled

By construction, not by prompting discipline alone — implemented in `portfolio.scenario.explanation.responseValidator.js`'s `validateExplanationText`, which runs on the parser's already-extracted `explanation` string (never on the raw JSON envelope): every finite number in the normalized input is collected into a known-value set (recursively, from the same JSON the model was given), every numeric token in the extracted text is checked against that set within a small rounding tolerance (absolute ±0.5, or ±1% relative for larger figures — either sign, since prose naturally drops an explicit minus when a word like "decline" already carries the direction). A number that traces to neither the known value nor its sign-flipped counterpart is treated as invented; `portfolio.scenario.explanation.service.js` retries once with a stricter re-prompt naming the specific unverified number(s) (or, if the envelope itself failed to parse, a re-prompt reiterating the required JSON shape), then fails with a `502 MalformedLLMResponseError` rather than ever returning an unverifiable figure to the client. No portion of the explanation is ever treated as authoritative on its own — the structured numbers already rendered on the page remain the source of truth regardless of whether an explanation is also shown.

## Difference between explanation and prediction

An explanation restates and contextualizes a number that already exists ("a 20% decline across Technology holdings would reduce the portfolio by approximately 10.4%, assuming all other holdings remain unchanged" — literally just prose around `sectorImpact`/`percentageChange`). A prediction asserts something about the future the AI has no basis for ("Technology is likely to decline 20% this quarter"). The implemented system prompt explicitly instructs the model to only restate/contextualize already-computed figures, never to add likelihood language, trade recommendations, or new numbers — mirroring the "no BUY/SELL/HOLD" constraint that already governs every other AI-touched surface in Athena (Sprint 8's AI Equity Research Analyst, Sprint 14's still-deferred Portfolio explanation layer).

## What changed between the Sprint 16 design and the Sprint 17 implementation

Nothing structural — the implementation matches this document's original constraints. Two decisions were made concrete during implementation, both narrower than the original design left open:

- **Opt-in per result, not automatic.** `ScenarioExplanationPanel.jsx` only calls `/explain` on an explicit "Explain this result" click — never on `/run` itself — so a user who never wants prose explanations never pays the LLM cost. `/compare` explanations were explicitly out of scope for Sprint 17; each scenario in a comparison would need its own explanation call, deferred until single-run explanation proves useful.
- **Not persisted.** Like scenario results themselves (see `portfolio.scenario.service.js`), an explanation is computed fresh on every call and never written to the database — there is still no `Scenario` collection to persist it against.
- **JSON envelope, not plain prose, over the wire.** Discovered only once real providers were exercised (see "Why the response is a JSON envelope, not plain prose" above) — the original design's "AI's only output is prose" framing is still true of what the *user* sees; it's no longer true of what the *provider* returns, which needed a parser Sprint 16's design didn't anticipate.

## Interview questions

1. **"What exactly is the AI allowed to see and do in Athena's scenario explanation feature?"** — Only the already-computed structured JSON response (rules, values, attribution, historical context, assumptions), copied through an explicit field allow-list in `portfolio.scenario.explanation.validator.js` — the same data a human reader already sees — and it may only rephrase/contextualize that in prose. It never computes a number, adjusts a shock value, fetches additional data, or assigns a probability or recommendation; there's no code path back into the resolver/calculator.
2. **"Why was this integration point designed a full sprint before it was built?"** — Writing the constraints down before any implementation existed meant Sprint 17 had no design decisions left to make under time pressure — only an existing, already-agreed contract to implement and test against. The risk being guarded against was a future "let's just have the AI pick a reasonable shock value" shortcut ever seeming like a small, reasonable addition.
3. **"How does Athena verify an AI-generated scenario explanation didn't hallucinate a number?"** — `portfolio.scenario.explanation.responseValidator.js` diffs every numeric token in the AI's output text against the structured input it was actually given (with a small rounding/sign tolerance for natural restatement); any number that doesn't trace back to the input is rejected. This is checkable mechanically, not just through prompt wording, because the AI's entire input is a closed, known set of already-verified numbers. A failed check triggers one stricter retry, then a `502` rather than ever showing an unverifiable number.
4. **"Why does a failed retry return an error instead of showing the explanation with a warning?"** — Because there is no way to tell a reader *which* number in a paragraph of prose is the fabricated one without re-flagging it inline (not built) — showing the whole paragraph with a vague disclaimer would still let the fabricated figure read as authoritative. Failing outright keeps the guarantee absolute: an explanation the user sees has passed the numeric check, or they see no explanation at all.
5. **"Why does the scenario explanation prompt ask for `{"explanation": string}` instead of plain text, when the whole point is prose?"** — Because two of the three configured LLM providers force JSON output at the HTTP transport level for every call (`openaiClient.js`, `geminiClient.js` — both built for Sprint 8's JSON research report and shared unconditionally), so "respond with plain prose" is a losing instruction against those providers regardless of wording. Asking for a minimal, known JSON shape and parsing the string out of it (`portfolio.scenario.explanation.responseParser.js`) works with the transport constraint instead of fighting it, and is provider-agnostic.
