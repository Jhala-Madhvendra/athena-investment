# Engineering Concept: The Comparable Valuation Engine (Pure, Framework-Independent Core)

## What it is

`backend/valuation/comps/comps.engine.js`, composed from `comps.formulas.js` (pure per-company math), `comps.statistics.js` (pure aggregation), and `comps.valuation.js` (pure target-application logic), is Sprint 7's calculation core: it takes a plain object describing a target company and its selected peers, plus a chosen statistic, and returns a plain object describing every derived metric, every multiple, per-multiple peer statistics, and the target's implied valuation under each applicable multiple. Like `dcf.engine.js`, it has zero dependencies on Express, MongoDB, or Yahoo Finance.

## Why we use it

Comparable Company Analysis has exactly the same "highest-stakes, most test-critical code" property DCF does (see `DCFEngine.md`), plus an additional wrinkle DCF doesn't have: it operates over an *array* of companies (one target, N peers) rather than a single company, so the engine has to be correct not just per-formula but across an aggregation step. Keeping that aggregation logic pure and I/O-free means a peer group's statistics can be hand-verified against a fabricated dataset (exactly as `comps.engine.test.js` does) without touching a database or a live market quote.

## Alternatives considered

- **One monolithic function that fetches data, computes multiples, aggregates statistics, and applies them to the target, all in `comps.service.js`.** Rejected for the same reason `dcf.engine.js` exists separately from `valuation.service.js` — mixing I/O with financial arithmetic makes both harder to test independently, and the DCF domain already proved the split is worth the extra file.
- **Reimplementing the Enterprise-Value-to-Equity-Value bridge inside `comps.valuation.js`** rather than importing `dcf.formulas.js`'s `netDebt()`/`equityValue()`. Rejected — it's the identical financial relationship regardless of how Enterprise Value was produced (see `research/finance/EquityValue.md`'s Sprint 7 addendum), and two copies of the same formula is exactly the kind of duplication that drifts out of sync over time.
- **A single `comps.formulas.js` file doing formulas, statistics, and target-application together.** Rejected in favor of three files split by concern (per-company math / cross-company aggregation / target application) — each has a genuinely different "unit" it operates over (one company / an array of numbers / one statistic + one target), which is a real seam, not an arbitrary one.

## Trade-offs

**For the pure-engine approach:** every layer — a single company's multiples, a peer group's statistics, a target's implied valuation — is independently unit-testable with hand-computed expected values (`comps.formulas.test.js`, `comps.statistics.test.js`, `comps.valuation.test.js`, `comps.engine.test.js`); the engine has no idea whether its data came from a live Yahoo quote or a hardcoded test fixture, which is exactly why the 76 backend Comps tests never touch a database or the network; determinism (`DeterministicCalculations.md`'s guarantees apply here too) is automatic since there's no I/O to make non-deterministic.

**Against it:** the boundary layer (`compsInput.mapper.js`, `comps.service.js`) has real translation work to do — converting Mongoose statement documents, Company documents, and Yahoo-shaped quotes into the engine's flat "company bundle" shape — and, as with DCF's CapEx-sign-convention bug, that boundary is exactly where a subtle mismatch (e.g. an EBITDA sign convention, or a stale field name) could hide undetected by the engine's own tests.

## How Athena implements it

`calculateComps({target, peers, statistic})` never validates its own input structurally (unlike `dcf.engine.js`, which gates on `dcf.validator.js` first) — because unlike DCF's assumptions, a comps engine call has almost nothing that can be *structurally* invalid once it reaches the engine; the real validation (peer list shape, ticker format, minimum peer count) happens one layer up, in `comps.validator.js`, before the engine is ever invoked (see `PeerSelectionEngine.md`). Inside the engine: `buildCompanyMetrics()` runs once per company (target and every peer) computing EBITDA, Enterprise Value, and all five multiples, each with a `{value, excludedReason}` pair rather than a bare number (see `OutlierHandling.md`); `buildPeerStatistics()` aggregates only the peers whose multiple wasn't excluded (see `StatisticalAggregation.md`); and for each multiple, `comps.valuation.js`'s `calculateImpliedValuation()` applies the requested statistic to the target's own metric. The final `valuationRange` is built by feeding the *set of applicable implied-per-share values* (not the raw multiples) back through the same `comps.statistics.js` summarizer used for peer aggregation — reusing one summarization function for two conceptually different things (peer-multiple spread, and cross-methodology valuation spread) because the underlying math (min/max/median of a set of numbers) is identical either way.

## Interview questions

1. *"Why does the Comps engine operate on 'company bundles' instead of Mongoose documents or raw Yahoo responses?"* — Same reasoning as `DCFEngine.md`: keeping the engine's input contract a plain, flat object means it can be unit-tested with fabricated data, reused regardless of where the data eventually comes from, and kept completely ignorant of Mongoose/Yahoo shape changes — only `compsInput.mapper.js` needs to know about those.
2. *"The engine reuses `comps.statistics.js`'s `summarize()` for both peer-multiple aggregation and the final valuation range. Is that appropriate reuse, or does it risk conflating two different concepts?"* — It's appropriate: both are, mathematically, "summarize this set of numbers into min/max/mean/median/percentiles" — the *meaning* of the numbers differs (a multiple vs. an implied per-share value) but the aggregation logic itself doesn't care, and duplicating it would only add a second place for the exact same min/median/max bug to live.
3. *"Why doesn't `comps.engine.js` know about the current market price?"* — Same separation of concerns as `dcf.engine.js` not knowing about it: market price is a *comparison* input, not a *calculation* input — the engine's job is to produce implied values from peer multiples, and `comps.service.js` (one layer up) is where the live quote is fetched and the upside/downside comparison against it is computed (`withMarketComparison()`), mirroring `valuation.service.js`'s identical pattern for DCF.
