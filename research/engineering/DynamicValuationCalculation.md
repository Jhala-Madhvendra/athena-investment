# Engineering Concept: Dynamic (Non-Persisted) Valuation Calculation

## What it is

Every Comps result is computed fresh, on request, from three live-at-request-time inputs: the target and peers' currently-stored financial statements, a live market quote per company, and the peers/statistic in the HTTP request body. Nothing about a completed Comps analysis — the peer list, the chosen statistic, the resulting multiples or implied values — is written to a database. This is the same discipline Sprint 6 already established for DCF (`research/product/DCFProductDesign.md`), applied to a second valuation domain.

## Why we use it

A Comps result is a function of three things that all change independently over time: the target/peers' financial statements (change quarterly/annually), live market prices (change constantly), and the user's own peer selection and statistic choice (changes every time they experiment). Persisting a "Comps analysis" as a saved object would immediately raise a question with no clean answer: is a saved result from three weeks ago still valid once the market has moved, or a peer has reported new earnings? Recomputing on every request sidesteps that question entirely — every result is, by construction, as current as the data behind it.

## Alternatives considered

- **Cache a completed Comps result keyed by (target, peer list, statistic).** Rejected for the same staleness reason above — a cached result would look identical whether it was computed one second or one month ago, silently misrepresenting its own freshness unless a lot of additional invalidation logic were built (and even then, a peer's underlying financials or the live quote could go stale independently of any cache-key change).
- **Persist a Comps "analysis" as a first-class saved object** (so a user could revisit it later without re-selecting peers). Considered, and explicitly deferred — the sprint brief requires that persistence, if ever added, first answer *why* it's needed, *what specifically* gets stored, and *how staleness gets handled* before any implementation begins. None of those three questions has been answered yet, so nothing is persisted (see Section "Data Storage" below).
- **Persist only the peer *selection* (not the calculated result), so a user's chosen peer list survives a page reload.** A reasonable, much narrower future feature — but still deferred for the same reason: it wasn't asked for, and even "just" persisting a peer list raises real questions (per-user? per-ticker? does it expire?) that haven't been worked through.

## Trade-offs

**For dynamic, non-persisted calculation:** the result the user sees is always consistent with what `/api/financials/:ticker` and `/api/market/:ticker` would currently return — there is no possibility of a Comps page showing a peer's stale market cap from three days ago while its own financial-statements page shows current data, because there's only ever one source of truth (today's live fetch), not a cached copy that could drift from it. It also means the engine and service layers stay simple: no cache invalidation logic, no "is this still fresh enough" check anywhere.

**Against it:** every `POST /:ticker/comps` request pays the full cost of fetching live quotes for the target and every peer (see `market.service.js`'s existing 60-second quote cache, which Comps benefits from automatically without any Comps-specific caching code) — there is no fast path for "the exact same request was just made a moment ago." For the scale and usage pattern this feature is built for (an analyst running a handful of comps per session, not thousands of automated requests per second), that cost is acceptable; it would need revisiting at a very different scale.

## How Athena implements it

`comps.service.js`'s `calculateComparableCompanyAnalysis()` has no read path to any "saved Comps result" collection — there isn't one. Every call re-fetches the target's statements (`financials.service.js`), the target and every usable peer's live quote (`market.service.js`, which already caches per-ticker for 60 seconds — reused, not duplicated), and re-runs the full `comps.engine.js` calculation. The response's `calculatedAt` timestamp (added at the service layer, exactly like DCF's) and `marketDataAsOf` (carried through from the live quote) are both explicit signals of *when* this specific result was computed, so a user comparing two Comps runs minutes apart can see they're not guaranteed to be identical even for the same peer list, if the market moved in between.

## Interview questions

1. *"A user runs the same Comps analysis (same ticker, same peers, same statistic) twice, five minutes apart, and gets two slightly different implied values. Is that a bug?"* — No — it's the expected, correct behavior of a system that deliberately never caches or persists a calculated result. The live market quote (and, less frequently, the underlying financial statements) can change between the two calls, and each call is defined to reflect *current* data, not a snapshot from the first call. The `calculatedAt`/`marketDataAsOf` timestamps in the response are exactly what lets a user recognize why the two runs differ.
2. *"What's the actual engineering cost of not persisting anything here, and when would that cost become a real problem?"* — The cost is redundant computation and redundant (though individually cheap, and already 60-second-cached) market-data fetches on every request — negligible for an analyst manually running a handful of comps. It would become a real problem under sustained high request volume (e.g. an automated batch process re-running the same analysis on a schedule) — at that point, a deliberately-scoped cache with an explicit staleness policy would be worth building, but that's a different, not-yet-justified feature.
3. *"If persistence were added later, what three questions does the team owe an answer to first, per this doc's own ground rules?"* — Why it's needed (what specific user problem does *not* recomputing solve that recomputing doesn't already solve well enough); what exactly gets stored (the raw peer selection? the full calculated result? both, separately, since they go stale at different rates?); and how staleness gets communicated or handled (does a saved result silently go stale, get a "last calculated" warning, or auto-refresh on view?). Building persistence without first answering these is exactly the shortcut this doc — and the sprint brief it's based on — was written to prevent.
