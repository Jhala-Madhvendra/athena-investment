# Advanced Portfolio Scenario Analysis

## 1. Definition

A portfolio scenario is a named set of hypothetical shock rules — "Market -15%," "Technology -25%," "AAPL -30%" — applied simultaneously to a user's current holdings to answer "how would my portfolio's value change if these specific, user-defined assumptions occurred?" Sprint 15 established the concept (single-stock, sector, portfolio-wide, and beta-based market shocks) but never actually shipped the engine — despite its commit message, no scenario code existed anywhere in the codebase before this sprint (confirmed by inspection: `git show --stat` on the Sprint 15 commit contains only transaction-ledger and historical-reconstruction files). Sprint 16 delivers the full engine: everything Sprint 15 described, plus multiple simultaneous shocks, explicit precedence when rules overlap, holding/sector attribution, Bear/Base/Bull presets, comparison, and sensitivity.

## 2. The formula

For each holding, exactly one rule governs its outcome (see `ScenarioAttribution.md`/`research/engineering/ScenarioPrecedence.md` for why never more than one):

```
Scenario Value(holding) = Current Value(holding) × (1 + EffectiveShock% / 100)
Portfolio Scenario Value = Σ Scenario Value(holding) over all holdings
Absolute Change = Portfolio Scenario Value − Current Portfolio Value
Percentage Change = Absolute Change / Current Portfolio Value × 100
```

A MARKET rule's `EffectiveShock%` is not the entered shock directly — it's `holding.beta × rule.shockPercent`, reusing Sprint 14's Portfolio Beta methodology exactly (see Section 6).

## 3. Intuition

A single-factor scenario ("what if Technology drops 20%") is a reasonable first question, but real market stress rarely arrives that cleanly — a broad selloff often comes with a market-wide move, sharper sector-specific damage, and a company-specific event all at once. A multi-factor scenario lets a user compose "Market -10%, Technology -20% additionally, AAPL -30% specifically" in one request and see the combined, non-double-counted result — closer to how an analyst actually reasons about a stress event.

## 4. Why investors use it

It turns "I think my portfolio is risky" into a specific, checkable number: "if Technology fell 25% and the broader market fell 15% at the same time, this portfolio would be estimated to lose $X, concentrated Y% in these three holdings." That's actionable context for position sizing and diversification conversations, without Athena ever telling the user what to do about it (see `research/product/AdvancedScenarioProductDesign.md`).

## 5. Assumptions

Every shock is **hypothetical and user-controlled** — never derived from historical data, never assigned a probability, never generated by AI (see `research/engineering/GroundedScenarioExplanation.md`). Historical volatility/beta/drawdown are shown alongside the result purely as *context*, and are structurally prevented from feeding back into the shock values themselves (see `HistoricalStressContext.md`). Only holdings with a live, USD-normalized current value participate; unpriced holdings are excluded and listed explicitly in `assumptions.unpricedHoldingsExcluded`, never silently dropped.

## 6. Limitations

Shocks are applied instantaneously and independently per holding — there is no cross-holding correlation model, no second-order effect (e.g., a Technology selloff dragging down a Financials holding that lends heavily to Technology firms isn't captured unless the user writes an explicit rule for it), and no path dependency (a -50% then +50% scenario isn't modeled as two sequential steps — a scenario is a single snapshot shock, not a simulated path). Sector/industry matching is an exact string match against `Company.sector`/`Company.industry` (Sprint 13's Yahoo-sourced classification) — a portfolio with unclassified holdings groups them under "Unclassified" rather than silently omitting their impact.

## 7. How Athena implements it

`backend/portfolio/portfolio.scenario.resolver.js` (rule precedence) and `portfolio.scenario.calculator.js` (the formula above, plus holding/sector attribution) are pure, dependency-free functions — no I/O, no MongoDB, no LLM — orchestrated by `portfolio.scenario.service.js`, which fetches current holdings (`portfolio.service.js`, Sprint 9), each ticker's sector/industry (`Company` model, Sprint 13) and beta (`marketService`, the same field Sprint 14's `portfolio.analytics.risk.js` reads), then hands everything to the pure engine. `POST /api/portfolio/scenarios/run` and `/compare` are the only two endpoints; nothing is persisted (see `research/product/AdvancedScenarioProductDesign.md` on why).

## 8. Common mistakes

- **Treating a scenario as a forecast** — "the portfolio will lose $60,000" instead of "if these assumptions occur, the modeled impact is -$60,000." Every response and UI surface is worded conditionally; see the sprint's own product principle.
- **Letting historical data quietly override a user-entered shock** — e.g., replacing a user's "-15%" with a computed "-11%" because that's what historical volatility suggested. Athena applies exactly what the user entered, always (`HistoricalStressContext.md`).
- **Stacking or multiplying overlapping shocks** (a Technology sector shock *and* an AAPL asset shock both hitting AAPL) instead of picking one via precedence — see `research/engineering/ScenarioPrecedence.md` for why this was rejected as a methodology.

## 9. Scenario vs. forecast

A scenario answers "what would happen *if* X" — a conditional statement about a hypothesis the user supplies. A forecast answers "what will happen" — an unconditional prediction Athena explicitly does not make anywhere in this feature. No probability is ever attached to a scenario (no "Bear Case: 20% likely"), which is the concrete, checkable difference between the two: a forecast without a probability or confidence interval isn't really a forecast, and a scenario with one stops being a clearly-labeled hypothetical.

## 10. How analysts use it

Portfolio managers and risk desks run exactly this kind of exercise — sometimes called desk-level or ad hoc stress testing — to answer "how exposed are we to a specific, articulable risk" ahead of a known catalyst (a rate decision, an earnings season, a geopolitical event) rather than waiting to observe the loss after the fact. The value is in the exercise of stating the assumption explicitly and tracing its consequence through the actual portfolio, not in the assumption being correct.

## 11. Interview questions

1. **"Why does Athena's portfolio scenario engine never look at historical data to pick a shock value?"** — Because doing so would substitute the user's stated hypothesis with a different one Athena invented, defeating the entire premise of "user-defined assumptions, transparently applied." Historical volatility/beta/drawdown are shown as separate, clearly labeled context instead — informative, never authoritative.
2. **"A user enters a Technology sector shock and an AAPL asset shock in the same scenario, and AAPL is a Technology holding. What happens to AAPL?"** — Only the AAPL-specific rule applies (Asset outranks Sector in Athena's precedence model) — never both added or multiplied together. The Technology rule still applies to every *other* Technology holding.
3. **"What's the difference between a scenario and a forecast, precisely?"** — A scenario is conditional ("if X, then modeled impact is Y") with the assumption fully under the user's control and no probability attached; a forecast is unconditional and implicitly claims some predictive confidence. Athena only ever produces the former.
