# Sprint 13 Reflection — Industry & Sector Intelligence

## What was built

A deterministic Industry & Sector Intelligence domain that answers "how does this company compare with the industry it operates in?" — the question none of Sprints 1–12 answered directly (every prior feature evaluates a company against its own history or its own intrinsic value, never against a peer reference set). `backend/industry/` (calculator, benchmark, peerDiscovery, service, formatter, validator, controller, routes — 8 files plus `__tests__/`), three API endpoints (`GET /api/industry/:ticker`, `/:ticker/peers`, `/:ticker/metrics`) returning a company-vs-industry comparison table, percentile positioning, deterministic relative strengths/weaknesses, and ranked potential-peer suggestions. A frontend Industry tab (`frontend/src/components/Industry.jsx` + `frontend/src/components/industry/`) added to the Company Intelligence nav between Earnings and News, plus a hand-off into Sprint 7's Comps peer picker via navigation state. 65 new backend tests and 9 new frontend tests (zero regressions across 726→791 backend / 106→115 frontend tests total), and 13 documentation files across `research/finance/`, `research/engineering/`, and `research/product/` (one, `OutlierHandling.md`, updated in place rather than duplicated). The optional AI explanation layer was designed in detail but deliberately not built this sprint — see "What was intentionally deferred."

## Finance concepts learned

The most consequential finance lesson was that a metric's value is only half the information — the other half is what's typical for the business it belongs to, and building the benchmark engine forced that into concrete code rather than a vague principle: the same 28% operating margin is a strength in one industry and unremarkable in another, and only a stated reference universe (not a vague "industry average") lets a reader judge which. The second lesson was percentile rank vs. percentile value (`FinancialPercentiles.md`) — Sprint 7's Comps only ever needed "what value sits at the 75th percentile," but Company Position needed the inverse question, "what percentile does this company's value sit at," which turned out to need genuinely new math (tie-aware rank), not a repurposing of the existing function.

## Engineering concepts learned

The clearest engineering decision was reuse discipline carried one layer further than Sprint 12's: `industry.calculator.js` computes nine metrics and reuses an existing formula for seven of them (`ratio.formulas.js` for margins/returns, `comps.formulas.js` for EBITDA/EV/P/E/EV-EBITDA) — the only genuinely new code is revenue growth (two-statement YoY, via `trend.engine.js`) and a debt-to-equity outlier override that had to live in the caller rather than the shared formula, since negative-equity exclusion is specific to cross-company benchmarking, not a universal property of the ratio (see `OutlierHandling.md`'s Sprint 13 addition). The second was caching at the right granularity: the target company is never cached (cheap, must be fresh), but the *reference universe* — the part whose cost scales with company count, not with a single request — gets a 5-minute in-memory cache keyed by industry/sector identity, verified in tests to eliminate redundant fetches on repeat calls for the same industry.

## Product decisions

"Potential Peers" and "selected peers" were kept as two clearly distinct concepts throughout — a ranked suggestion list versus Sprint 7's user-curated Comps set — with the hand-off between them implemented as a pure UI pre-fill (navigation state into `ComparableCompanies.jsx`'s existing `addPeer()`), never an automatic peer-set mutation. Every benchmark states its reference-universe size and level explicitly, never "industry average," per the brief's own instruction — this shaped both the API response shape (`universe: {level, key, size, note}` as its own object) and the frontend copy. Valuation multiples (P/E, EV/EBITDA) are deliberately never classified as a strength or weakness, only percent-based operating metrics are — trading at a premium isn't inherently good or bad, and the classification logic enforces that distinction structurally, not just in copy.

## Why industry context is different from comparable company analysis

Comps (Sprint 7) is a user-curated peer set producing an implied per-share valuation — a deliberate, narrow, high-stakes calculation. Industry Intelligence is a broader, automatically-assembled reference set producing relative operating and valuation context — no implied valuation output, ever. The two features can hand off to each other (a suggested peer can seed the Comps picker) but neither replaces the other's core judgment: Comps still requires explicit human curation before any number is calculated from it.

## Reference universe decisions

Investigation confirmed Athena has no external "list every company in industry X" data source — the only companies it knows about are ones a user has previously searched or imported, the exact limitation Sprint 7's `PeerSelection.md` already documented for its own peer browsing. Rather than either fabricating a broader universe or silently benchmarking against whatever happened to be available, `industry.peerDiscovery.resolveReferenceUniverse()` requires imported financial statements (not just a matching label) for universe membership, falls back from `industry`-level to broader `sector`-level matching when too few companies share the exact industry, and always states which level was actually used and why.

## Minimum sample size decisions

A single threshold, `MIN_UNIVERSE_SIZE = 4`, shared between `industry.benchmark.js` (gates mean/median/percentile computation per metric) and `industry.peerDiscovery.js` (gates whether a universe level counts as "sufficient" at all) — imported from one module into the other specifically so the two questions ("is this universe usable" and "is this metric's sample big enough") never quietly disagree. Below the threshold, a metric is reported as unavailable with a stated reason rather than computed anyway on a sample too small to be meaningful.

## Mean vs. median decisions

Every comparison, positioning, and classification decision uses the median, never the mean — the same rationale Sprint 7's Comps already established (a single atypical peer shifts a mean by its full distance but a median by at most one rank), applied here to operating metrics as well as valuation multiples. The mean is still computed and returned in the API response for completeness, but it never drives strength/weakness classification or the headline comparison table.

## Outlier handling decisions

No statistical outlier trimming (z-score, IQR) anywhere — consistent with Sprint 7's existing philosophy (`OutlierHandling.md`), Industry Intelligence only excludes values that are not economically meaningful (zero/negative denominators), always with a stated reason, never silently. One new wrinkle this sprint: debt-to-equity needed an exclusion rule *stricter* than the shared `ratio.formulas.js` function provides (negative equity is numerically computable but not meaningful for cross-company leverage comparison) — resolved by adding the stricter rule at the `industry.calculator.js` call site rather than changing the shared formula's behavior for every other caller.

## Peer discovery decisions

`industry.peerDiscovery.rankByMarketCapProximity()` deliberately mirrors a heuristic Athena had already privately proven — `ai.contextBuilder.js`'s `selectAutoPeers()` (same-sector, closest-market-cap ranking, built for Sprint 8's AI report context) — rather than inventing a new signal or a genuine similarity-scoring model Athena's current data can't support responsibly. It's exported as a pure, standalone function specifically so a future automatic-peer-selection system could reuse it without duplication, without that system being built this sprint.

## Why peers remain user-selected for Comps

Unchanged from Sprint 7, and deliberately reaffirmed rather than quietly eroded: `comps.peerSelector.js`, `comps.validator.js`, and `comps.service.js` are untouched by this sprint. The "Use for Comparable Analysis" action only pre-fills the existing peer picker via navigation state — functionally identical to a user manually searching for and clicking "Add" on that same company — and the user must still explicitly review the pre-filled list and click Calculate before anything is computed.

## Data freshness decisions

Financial-statement-derived metrics (margins, growth, ROE, ROA, FCF margin) and market-derived metrics (P/E, EV/EBITDA) are never presented as if measured at the same instant — the API response carries `dataFreshness.financialPeriod` (the target's latest fiscal year) and `dataFreshness.marketDataAsOf` (the live quote timestamp) as two separate fields, and the frontend renders both. Universe members can individually be on slightly different fiscal-year cadences; nothing in the response papers over that.

## Caching decisions

A 5-minute in-memory cache over the *assembled reference-universe bundle* (financial + market metrics together), keyed by `level:key`, mirroring `market.service.js`'s existing `Map`+`expiresAt` pattern — no new infrastructure dependency. The target company's own data is never cached. `GET /api/industry/:ticker/peers` deliberately reuses the same cache entry `GET /api/industry/:ticker` populates, so the expected navigation order (view the main page, then view peers) costs no extra fetches.

## What was intentionally deferred

The optional AI explanation endpoint (designed in `research/engineering/GroundedIndustryExplanation.md`, not built — the sprint brief explicitly frames it as optional and forbids AI from calculating benchmarks or judging "best" in any form); a genuine industry-similarity/classification taxonomy beyond Yahoo's free-text sector/industry strings (blocked by data availability, not effort — no such provider abstraction exists in Athena today); and product-analytics instrumentation for the metrics `IndustryIntelligenceProductDesign.md` §10 identifies as worth watching (page views, comparison interactions, peer-to-Comps conversion) — described as worth measuring, not implemented without real usage to justify it, per the brief's own caution.

## Challenges

Deciding where the debt-to-equity outlier override belonged was the sprint's most genuinely judgment-laden engineering call — the shared `ratio.formulas.debtToEquity()` function's existing behavior (exclude only a zero denominator) is correct for its other callers, so the stricter negative-equity exclusion needed for cross-company benchmarking had to be layered on top at the Industry-specific call site rather than changing shared behavior everyone else depends on. A second challenge was avoiding double-counting valuation multiples as strengths/weaknesses — the first implementation draft classified P/E and EV/EBITDA the same way as margins before re-reading the brief's explicit "never conclude cheap or expensive" instruction and restricting `classifyPosition()` to percent-unit metrics only.

## Future improvements

A genuine industry-classification taxonomy (GICS-style codes) if Athena ever integrates a provider that supplies one, replacing today's free-text sector/industry string matching. The AI explanation endpoint, using the grounding design already written up in `GroundedIndustryExplanation.md`. A confidence indicator on a benchmark proportional to how far above the minimum sample size the universe actually is, rather than a binary available/unavailable. Extending `rankByMarketCapProximity()`'s reuse into an actual future automatic-peer-selection system, as scoped (but not built) in `research/engineering/PeerDiscovery.md`.

## Finance interview questions

1. **"Why can't a company's operating margin be evaluated without industry context?"** — Because cost structure and competitive dynamics vary enormously by business model — the same margin number is exceptional for one industry and mediocre for another. Industry Intelligence exists specifically to attach that missing reference point to every metric Athena already computes.
2. **"Walk through why Athena reports a percentage-point difference for margins but a relative multiple ('1.3x') for P/E."** — They're different kinds of numbers. A margin is itself already a percentage, so an additive percentage-point comparison directly states "how many more cents of profit per revenue dollar." A P/E is a ratio, so a multiplicative comparison ("1.3x the median") is the natural way to express "how much more expensive relative to peers" without conflating a ratio-of-a-ratio into a misleading additive figure.
3. **"Why does Athena default every industry comparison to the median instead of the mean?"** — The median is far less sensitive to a single atypical company in a small, imperfectly-curated reference universe — the same reasoning Sprint 7 already established for peer trading multiples, applied here to operating metrics as well.
4. **"What's the difference between 'the value at the 75th percentile' and 'this company's percentile rank'?"** — The first is a threshold (what value would a company need to reach the top quartile); the second is where a specific company's actual value falls within the distribution. Athena needed to build the second one new — `comps.statistics.percentile()` only ever computed the first.
5. **"Why does Athena require at least 4 reference-universe companies before computing any statistic, not just percentiles?"** — Because a mean or median computed from 2-3 companies is barely more informative than the raw values themselves, and presenting it with the same confidence as a larger-sample statistic would overstate what the data actually supports.
6. **"How does Industry Intelligence differ from Comparable Company Analysis?"** — Comps is a small, user-curated peer set producing an implied per-share valuation. Industry Intelligence is a broader, automatically-assembled reference set producing relative operating/valuation context — it never produces an implied valuation.
7. **"A company trades at 1.3x its industry median P/E. What can you actually conclude?"** — Only that the market currently prices it at a premium to its immediate reference set — not whether that premium is justified by superior growth/quality or reflects overvaluation. Athena deliberately never resolves that ambiguity into a "cheap"/"expensive" label.
8. **"Why does Athena exclude negative-equity companies from the debt-to-equity benchmark, even though the ratio is technically computable?"** — A negative denominator makes the ratio numerically produce a value but not a meaningful cross-company leverage comparison — it's a distress signal, not a leverage read. Athena excludes it with a stated reason rather than letting a numerically-valid-but-meaningless number distort the benchmark.
9. **"How does Athena avoid calling a below-median metric a 'weakness' when the gap is trivial?"** — A materiality threshold (3 percentage points by default) — differences smaller than that are classified as neutral, not weaknesses, since small gaps are as likely to reflect noise or timing as a genuine structural difference.
10. **"Why does Athena state the reference universe's size on every industry comparison?"** — Because "industry average" implies a completeness Athena's tracked-company database doesn't have. Stating the actual count lets a reader calibrate how much weight the comparison deserves, rather than assuming it's drawn from a comprehensive market dataset.

## Product Management interview questions

1. **"What's the core product question Sprint 13 answers, and how is it different from every prior sprint?"** — "How does this company compare with the industry it operates in?" Every prior sprint evaluated the company against its own history (Business Analysis), its own intrinsic value (DCF), or a user-picked peer set (Comps) — none automatically calibrated its numbers against a broader reference set.
2. **"Why is Industry Intelligence a separate tab instead of folded into Business Analysis or Comps?"** — It's a structurally different comparison axis (against a reference universe, not against the company's own history or a user-curated peer set) — merging it into either existing tab would conflate two different mental models a reader needs to hold separately.
3. **"Why doesn't 'Potential Peers' automatically become the Comps peer set — wouldn't that save the user a step?"** — Because it would quietly convert a suggestion the user is expected to scrutinize into a default they're likely to accept without scrutiny — exactly the failure mode Sprint 7 built manual peer selection to prevent. Saving a click isn't worth eroding that safeguard without real evidence users want that trade-off.
4. **"How did you decide the materiality threshold for strengths/weaknesses (3 percentage points)?"** — A documented, tunable default balancing two failure modes: too low a threshold produces noisy, low-signal strength/weakness lists; too high a threshold hides genuinely notable gaps. It's a judgment call, made explicit as a named constant rather than an unstated magic number, so it can be revisited with real usage data.
5. **"Why does the sprint forbid AI from calculating any part of the benchmark?"** — A benchmark has exactly one correct value given a reference universe and target — there's no legitimate role for a model to play in computing it, only in explaining an already-computed, already-verified number. Letting AI calculate would reintroduce exactly the hallucination risk every other Athena AI feature is designed to avoid.
6. **"What would you cut first if this sprint had half the time?"** — The frontend's percentile-position visualization (`PositioningBars`) — it's additive context on top of the comparison table and strengths/weaknesses list, which are the load-bearing core; the feature is still coherent and useful without it.
7. **"How do you know 'Potential Peers' and 'Comps peer set' are actually understood as different things by users, not just different in the code?"** — Genuinely unverified — this is one of the open user-research questions in `IndustryIntelligenceProductDesign.md` §10, not something this sprint's UI copy alone can guarantee lands correctly.
8. **"Why does the Industry tab sit between Earnings and News in the navigation?"** — It follows a natural reading flow: a user has already seen the company's own results (Earnings) and is about to check external context (News) — industry comparison is a natural bridge between "how did we do" and "what's happening around us."
9. **"What's the single biggest reason a benchmark might show 'not available' instead of a number?"** — Insufficient reference-universe sample size — fewer than 4 tracked companies share the target's industry (even after falling back to sector) with imported financial statements for that specific metric.
10. **"If a stakeholder asked why Athena doesn't build a full industry-classification taxonomy this sprint, what would you say?"** — No such data source exists in Athena today, and inventing one (hand-classifying companies) would violate the brief's explicit "do not hard-code classifications for a handful of companies as a production solution" instruction. Reusing Yahoo's existing sector/industry strings, with their acknowledged limitations documented, is the honest trade-off versus either fabricating a taxonomy or blocking the sprint on a data-source project.

## Engineering / AI interview questions

1. **"Walk through the one Industry Intelligence calculation that couldn't just reuse an existing formula."** — Percentile rank (`industry.benchmark.percentileRank()`) — `comps.statistics.percentile()` already existed but answers the inverse question (value at a percentile, not percentile of a value). Everything else (margins, ROE, P/E, EV/EBITDA, mean/median/percentile-value) reuses `ratio.formulas.js`/`comps.formulas.js`/`comps.statistics.js` directly.
2. **"How is `industry.calculator.js` kept deterministic, and how do you know it actually is?"** — No network/database/random/wall-clock calls inside it — every function is a pure transformation of statement documents and a market cap already passed in. 65 tests assert exact output values for fixed inputs, including edge cases (zero denominators, negative earnings, missing prior-year statements).
3. **"Why does the universe-bundle cache key on `level:key` instead of the target ticker?"** — Because the reference universe is shared across every company in the same industry — two companies in "Software" should hit the same cache entry, not each maintain a redundant copy of the same underlying peer data.
4. **"You designed the debt-to-equity outlier override at the calculator layer instead of the shared formula. What would have gone wrong the other way?"** — Changing `ratio.formulas.debtToEquity()`'s own exclusion rule would have altered behavior for every existing caller of that function, not just Industry Intelligence — a change with a much larger, less-understood blast radius than adding a domain-specific override at the one call site that actually needed the stricter rule.
5. **"Why was the AI explanation layer fully designed in a document but not implemented, rather than skipped entirely?"** — Because the design decisions (evidence allow-list shape, citation validation, retry pattern) are the genuinely hard part of adding AI to a deterministic feature safely, and they're best made deliberately against Athena's proven Sprint 8 precedent rather than rushed at the end of an already-large sprint. Writing it down turns a vague future feature into a scoped, immediately-buildable task — exactly the same call Sprint 12 made for `GroundedEarningsExplanation.md`.
