# Sprint 17 Reflection — Grounded Scenario Explanation

## What was built

An optional, opt-in AI layer that explains a scenario result already computed by Sprint 16's engine — implementing exactly the integration point `research/engineering/GroundedScenarioExplanation.md` designed and deliberately deferred a sprint earlier. New backend modules: `backend/portfolio/portfolio.scenario.explanation.{validator,promptBuilder,responseValidator,service}.js`, wired into the existing `portfolio.scenario.controller.js`/`portfolio.scenario.routes.js` as `POST /api/portfolio/scenarios/explain`. The endpoint takes the client's own already-received `/run` (or one `/compare` entry) response, validates it against an explicit field allow-list, prompts the configured LLM provider (`backend/ai/providers/`, reused unchanged) to explain it in plain prose, mechanically verifies every number in the response traces back to the input it was given, and returns the explanation — never recomputing the scenario itself. New frontend: `ScenarioExplanationPanel.jsx`, an "Explain this result" button on `ScenarioResult`, mirroring the AI Research Analyst page's generate-on-click pattern. A small secondary deliverable rode alongside: `assumptions.sectorCoveragePercent`/`industryCoveragePercent`, value-weighted coverage figures parallel to Sprint 14's `betaCoveragePercent`, computed from data the scenario context already fetches. 12 new backend tests across 4 new suites plus additions to the existing scenario service/routes suites (full backend suite: 102/102 passing in `backend/portfolio`), and a new frontend suite for the explanation panel (15/15 passing across all three affected scenario test files, confirming no regression to `ScenarioSection`/`ScenarioBuilder`). Two documentation updates: `GroundedScenarioExplanation.md` promoted from a deferred design to an as-implemented record, and a new `research/product/ScenarioExplanationProductDesign.md`.

## Finance concepts learned

Distinguishing "explaining a number" from "adding a claim about a number" turned out to be a real financial-communication line, not just a prompting nuance. "Technology contributes 61% of this scenario's impact" restates `contributionToScenarioImpactPercent` — an explanation. "Technology is the riskiest sector in this scenario" injects an evaluative claim Athena's own numbers don't make (risk isn't ranked anywhere in the response) — the same discipline as Sprint 16's own "largest modeled impact, never 'most dangerous'" rule, now enforced on free-form prose rather than fixed UI copy, which is a harder surface to police.

## Engineering concepts learned

The bigger lesson only surfaced once a real provider was exercised in the browser, past what unit tests (which mock the provider entirely) could catch: `llmProvider.generateReport()` is shared by every AI feature in Athena, and two of its three concrete providers — `openaiClient.js` and `geminiClient.js` — hard-code forced JSON output at the HTTP transport level (`response_format: json_object`, `responseMimeType: application/json`), added for Sprint 8's JSON research report and inherited unconditionally by anything reusing `generateReport`. The explanation feature's first version asked the model for "plain prose only, no JSON" — an instruction that cannot actually turn off a transport-level constraint, so the model resolved the contradiction by JSON-encoding its own JSON object as an escaped string, and that raw, doubly-encoded text reached the UI verbatim (caught by manual testing, not a unit test — every mocked test for the first version passed cleanly, because the mocks never exercised what a forced-JSON provider actually returns). The fix treats "JSON envelope" as the real contract (`{"explanation": string}`, extracted by a new `portfolio.scenario.explanation.responseParser.js` mirroring `ai.responseParser.js`'s existing recovery pattern) instead of fighting a constraint that isn't actually optional. The mechanical hallucination check also needed a smaller, separate fix: a sign-tolerant match, since prose naturally drops an explicit minus when a word like "decline" already carries the direction (`percentageChange: -12` restated as "a decline of approximately 12%" was initially flagged as an invented number).

## Why this is a lesson about testing, not just prompting

Every unit test for the original "plain prose" version passed, because `llmProvider.generateReport` was mocked and the mock never encoded the actual constraint (forced JSON mode) that real OpenAI/Gemini calls carry. The tests verified the code did what it was told; they couldn't verify the *instruction itself* was achievable against the real provider. The gap only closed once the feature was exercised end-to-end against a live provider — the same reason Sprint 16's reflection notes a real running-browser pass caught things a mocked test suite couldn't.

## Product decisions

The most consequential call was keeping this strictly opt-in per single scenario result, with `/compare` explanation and persistence both explicitly out of scope — not because either is hard, but because neither had a validated need yet, the same "infrastructure ahead of usage data" concern Sprint 16 raised about scenario persistence generally. The second was treating a failed verification as a hard `502`, never a hedged or partially-shown explanation — there's no reliable way to flag which specific sentence in a paragraph is wrong, so the only trustworthy failure mode is showing nothing.

## Why the explanation layer never touches the scenario engine

`portfolio.scenario.explanation.service.js` has no import of `portfolio.scenario.resolver.js` or `portfolio.scenario.calculator.js`, and no code path writes back into them. The endpoint's only inputs are a JSON body from the caller and its own prompt/validation modules — architecturally, it cannot influence a scenario's numbers even if a future change tried to make it, because there's no shared state or return value for it to affect.

## Why sector/industry coverage was added here

It uses data `portfolio.scenario.service.js`'s `loadScenarioContext` already fetches (`Company.sector`/`Company.industry`) — no new provider call, no new field on `Company`. It rode along with this sprint because it was small enough not to warrant its own sprint, not because it's related to the explanation feature functionally; the two are independent additions to the same `assumptions` block.

## Challenges

The forced-JSON-provider bug (see "Engineering concepts learned") was the sprint's real challenge — not because the fix was hard once understood, but because nothing in the unit test suite could have surfaced it; it was only visible by actually running the feature in the browser and reading the rendered output, which showed a raw, doubly-escaped JSON string where prose was expected. The sign-tolerance issue was a smaller, second correction caught by a unit test. Everything else followed directly from the constraints `GroundedScenarioExplanation.md` had already written down a sprint earlier — the shock was in the transport layer, not the explanation design itself.

## Limitations

The hallucination check is numeric-only — it cannot catch a response that uses only real numbers but draws a wrong or unsupported qualitative conclusion from them (e.g., correctly citing `contributionToScenarioImpactPercent` but mischaracterizing what it means). No explanation is cached; every click re-calls the LLM, including re-explaining an identical result. `/compare` scenarios have no explanation surface yet — a user comparing three scenarios must (if this becomes valuable) currently read three separate `/run` explanations, one at a time, outside the comparison view.

## Future improvements

Comparison-level explanation ("why did Bear Case lose more than Base Case"), once single-run explanation's usage justifies it. A short-lived, session-scoped cache keyed on the normalized scenario result, if repeat re-explains of an unchanged result turn out to be common. Extending the same grounded-explanation pattern to Sprint 14's still-deferred `GroundedPortfolioExplanation.md`, now that this sprint is a second, working reference implementation of the same design discipline rather than a first attempt.

## Finance interview questions

1. **"Why can't Athena's scenario explanation AI say a scenario result is 'concerning' or 'risky'?"** — Because that's an evaluative claim about severity or desirability that none of Athena's own computed numbers make — the response contains magnitudes and attribution, not a risk rating. Adding one in prose would inject an opinion the structured data never asserted, breaking the same neutral-register discipline Sprint 16 established for fixed UI copy.
2. **"If a scenario's `contributionToScenarioImpactPercent` for a sector is negative, could the AI explanation legitimately say that sector 'helped' the portfolio?"** — Yes, and it should — that's exactly what a negative contribution against a net loss total means (this sector's change ran opposite the portfolio's overall direction), and restating that correctly is squarely within the explanation layer's job description.
3. **"Why does the explanation prompt tell the model not to round a dollar figure to 'a million' scale?"** — Because doing so would make the mechanical hallucination check unable to verify the number (its literal-tolerance match wouldn't recognize "$1.2 million" as a restatement of $1,234,567), and more importantly because Athena already displays the exact figure elsewhere on the same page — an approximated restatement would visually disagree with the number right above it.

## Product Management interview questions

1. **"Why ship AI explanation for `/run` before `/compare`, given comparison is arguably the more complex, higher-value case?"** — Single-run explanation answers a narrower, well-defined question and was faster to validate; comparison explanation's harder question ("why did these differ") deserves its own design pass once there's evidence users actually want prose explanations for scenario results at all.
2. **"How would you tell if this feature is worth the LLM cost it adds?"** — Explain-click rate as a share of scenario runs is the direct signal — a low rate across many scenario runs would suggest the tables alone are already sufficient for most users and the feature isn't earning its cost.
3. **"Why show a hard error instead of a "some numbers below may be unverified" warning when the check fails?"** — Because a paragraph-level warning doesn't tell the reader which sentence to distrust, which in practice means the whole paragraph becomes unusable anyway — showing nothing is more honest than showing something the user can't tell how to partially trust.

## Engineering / AI interview questions

1. **"Walk through how `portfolio.scenario.explanation.responseValidator.js` decides a number is hallucinated."** — It runs only on the already-extracted `explanation` string (`portfolio.scenario.explanation.responseParser.js` pulls that string out of the model's raw `{"explanation": ...}` JSON envelope first) — it recursively collects every finite number from the exact JSON object the model was given, extracts every numeric-looking token from the extracted text, and for each checks whether it falls within a small absolute/relative tolerance of a known value or that value's sign-flipped counterpart (to allow natural phrasing like "a decline of 12%" for a stored `-12`). Anything outside that tolerance band, and above a small "always allowed" magnitude for ordinary counting numbers, is reported as unverified.
2. **"Why does the scenario explanation feature ask the model for `{"explanation": string}` JSON instead of the plain prose it actually displays?"** — Because `openaiClient.js` and `geminiClient.js` force JSON output at the transport level for every call through the shared `generateReport` interface (added for Sprint 8's research report), so a "plain prose, no JSON" instruction cannot actually be honored by those providers — the model resolves the contradiction by inventing its own JSON wrapper, which is worse and harder to parse reliably. Asking for one specific, known JSON shape and extracting the string from it is provider-agnostic and matches what the transport layer already guarantees for two of three providers.
3. **"Why retry once with a stricter prompt instead of just failing immediately on a parse or verification failure?"** — Mirrors `ai.service.js`'s existing retry pattern for the research report: a model occasionally makes a one-off formatting, envelope-shape, or rounding slip it can self-correct given the specific reason it failed, and one bounded retry catches that without risking an unbounded retry loop on a genuinely stubborn response.
4. **"The endpoint is called `/explain` and takes a full scenario result as its body instead of scenario parameters like `/run` does — why?"** — Because it explains a result the caller already has, not one it needs computed — recomputing it would mean fetching portfolio/market/company data a second time for work already done, and would reopen the question of whether the explanation and the currently-displayed result could ever drift out of sync. Passing the result directly guarantees the explanation is always about exactly what's on screen.
