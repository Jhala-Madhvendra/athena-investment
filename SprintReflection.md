# Sprint 3 Reflection — Business Intelligence Engine

## What was built

A Business Intelligence Engine that turns stored financial statements into the kind of read an analyst would give a client: growth (Revenue/Net Income/Operating Income/FCF/Debt/Equity/Asset CAGR), trend direction on margins and returns, a weighted 0–100 Financial Health Score across five components (Profitability, Liquidity, Solvency, Cash Flow, Growth), and 5–7 auto-generated, human-readable insights — all exposed via `GET /api/analysis/:ticker` (plus lightweight `/trends`, `/insights`, `/health-score`, and `/batch` variants) and rendered as a new "Business Analysis" tab. The pipeline follows the architecture strictly: `Financial Statements → Trend Engine → Insight Engine → Health Score → Response Formatter → Frontend`, reading only from MongoDB via Sprint 2's existing `financials.service`/`ratio.formulas` — never Yahoo Finance directly.

## Finance concepts learned

CAGR only means something once you've handled the cases where it doesn't: a company can't have a CAGR from a zero or negative starting value (undefined growth), and a negative ending value makes the exponent produce nonsense rather than a real "-40%" figure — both had to resolve to explicit sentinels (`infinite`, `N/A`) instead of `NaN` leaking into a UI. The Health Score's weighting scheme was the deeper lesson: five components scored independently (Profitability, Liquidity, Solvency, Cash Flow, Growth) and combined with configurable weights (balanced/growthFocused/safetyFocused) is what lets the same underlying numbers answer different investor questions — a growth investor and a value investor should not see the same composite score dominate the same way. And debt is the one metric where "growth" is inverted: rising debt is bad, so its CAGR gets scored on an inverted curve rather than reusing the revenue-style normalizer — coding that mechanically without checking the polarity would have silently rewarded companies for taking on debt.

## Engineering concepts learned

The most valuable lesson this sprint wasn't in the engines — they were already well-built — it was in **not trusting "it compiles" as "it works."** Every one of the following passed a code read and only broke under an actual test: a validator that checked `financialData.incomeStatement` as an array when the real shape was `{statements: [...]}`, silently 404-ing every ticker; two DB-retrieval functions stubbed to return empty data; a health-score input with hardcoded placeholder ratios (`currentRatio: 1.5`) standing in for real numbers; insight templates referencing `{CAGR}` when the context object held `cagr` (case-sensitive, so it never matched); a rule evaluator returning `type: 'declining'` for a template tree that had no top-level `declining` key, silently dropping the one insight investors most need to see; and a frontend field (`trends.operatingMargin`) sent as a bare string while the component read `.direction` off it, rendering blank instead of throwing. None of these surfaced in a syntax check or even a shallow "does it return 200" smoke test — they needed real data, a hand-verified expected output, and a rendered screenshot to catch. See [research/engineering/TrendEngine.md](research/engineering/TrendEngine.md), [InsightEngine.md](research/engineering/InsightEngine.md), and [ScoringEngine.md](research/engineering/ScoringEngine.md) for the engine designs themselves.

## Product decisions

Keeping the module boundary hard — Trend Engine only reads what `transformFinancialData` hands it, Insight Engine only reads `trends`/`ratios`, Health Score only reads component scores plus weights — meant every layer could be hand-verified in isolation with a fabricated dataset before ever touching a live company, which is exactly how the CAGR and weighting bugs got caught early. The decision to thread a ticker/company name into the Insight Engine (`generateInsights(trends, ratios, companyName)`) rather than hardcode "the company" was small but mattered: "AAPL shows a mix of strengths and weaknesses" reads like analysis; "The company shows..." reads like a template.

## Challenges faced

The hardest bug wasn't in this sprint's code at all — the Liquidity component scored 0 for every company, and the first explanation ("Apple files an unclassified balance sheet, Yahoo just doesn't have the field") was plausible, cited real accounting practice, and was wrong. Testing it against the live Yahoo API with a broad sweep of candidate field names took five minutes and found the real cause: Sprint 2's provider requested `annualTotalCurrentAssets`, and the actual field is `annualCurrentAssets` (no "Total"). The lesson: a plausible-sounding root cause is not a verified one, and when the fix is cheap to test empirically, test it before writing it into a report.

## Future improvements

- Insight templates currently pick the first-declared phrasing per type (`for...in` breaks after one iteration) — the alternate phrasings authored alongside them are dead code. Selecting among them based on sub-conditions (e.g., accelerating vs. steady growth) would use content that's already written.
- `evaluateStability`'s "mixed signals" insight only counts strong/weak signals, it doesn't track *which* categories were strong or weak — surfacing that would let the insight name the actual tension (e.g., "margins improving, but liquidity tightening") instead of a generic mixed-signal statement.
- The Health Score is the natural input to a portfolio screener (`/api/analysis/batch` already exists) — a ranked comparison view across tickers is the obvious next consumer.

## Interview story

*"In Sprint 3 I built a Business Intelligence Engine — trend detection, CAGR-based growth metrics, a weighted financial health score, and rule-based natural-language insights — on top of an existing ratio engine. The interesting part wasn't designing those engines; they were already well-designed. It was discovering, only through actually running the thing end-to-end with real data, that almost none of it was wired up correctly: a validator checking the wrong shape was silently 404-ing every request, insight templates referenced context keys that didn't exist so they rendered literal unfilled placeholders, and one rule branch had no matching template at all — which meant the single most important insight, a declining-revenue warning, silently disappeared exactly when an investor needed it most. None of that showed up in a syntax check; it only showed up once I hand-verified CAGR math against a manual dataset and read the actual rendered output. The other habit that paid off was distrusting my own first explanation: when a liquidity score kept coming back zero, my first theory — that Apple's balance sheet just doesn't report that field — sounded right and cited real accounting practice, but I tested it against the live API instead of writing it down, and found the actual bug was a one-word field-name typo in the provider. That's the general principle I'd carry forward: a plausible root cause and a verified one are different things, and when verification is cheap, there's no excuse to skip it."*
