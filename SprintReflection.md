# Sprint 16 Reflection — Advanced Portfolio Scenario Analysis & Stress Testing

## What was built

A multi-factor portfolio scenario and stress-testing engine — with a significant scope correction at the start: inspection of the Sprint 15 commit before writing any Sprint 16 code (`git show --stat`) showed that despite its commit message, no scenario/stress-testing code had actually shipped — only transaction-ledger and historical-reconstruction work (`portfolioHistory.service.js`, `holdingsReconstruction.calculator.js`) existed. Sprint 16 therefore built the entire scenario engine from the ground up: single-asset, sector, industry, portfolio-wide, and beta-based market shocks, explicit precedence when rules overlap, holding- and sector-level attribution, Bear/Base/Bull plus three additional presets, custom multi-rule scenarios, scenario comparison, and single-factor sensitivity analysis. New backend modules: `backend/portfolio/portfolio.scenario.{resolver,calculator,presets,validator,service,controller,routes}.js` — pure rule/attribution engine, orchestration, and two endpoints (`POST /run`, `POST /compare`, `GET /presets`), mounted at `/api/portfolio/scenarios`. New frontend: a `ScenarioSection` appended to the existing Portfolio page (`frontend/src/components/portfolio/scenario/`: `ScenarioBuilder`, `ScenarioResult`, `HoldingImpactTable`, `SectorImpactTable`, `SensitivityPanel`, `ScenarioComparisonView`) — the original Portfolio page and every prior section were left untouched. 69 new backend tests across 6 suites joined the pre-existing suite with zero regressions (1080 total, 95 suites, confirmed by full-suite reruns after every major component). 6 new frontend tests exercise the full user flow (empty state, preset loading, rule building, scenario run, error handling, comparison) using `@testing-library/react` and `userEvent` — the first frontend component tests written for the Portfolio page's newer sections, added because the feature's interaction surface (multi-step rule building, precedence, comparison) was judged complex enough to warrant it, unlike Sprint 14's simpler read-only sections. The feature was also driven end-to-end in a real, running browser via Playwright (backend + Vite dev server, both started fresh) — added a holding, built a custom rule, ran a scenario, verified attribution/historical-context/assumptions rendered correctly, loaded the Bear Case preset, and produced a working scenario comparison chart, with zero console errors and zero failed network requests. Twelve new documentation files across `research/finance/`, `research/engineering/`, and `research/product/`, plus this reflection.

## Finance concepts learned

The sharpest lesson was that "portfolio weight" and "contribution to scenario impact" are not the same axis and actively mislead when conflated — a 1%-weight holding shocked -80% can explain 100% of a scenario's total dollar loss while a 99%-weight untouched holding explains 0%, and a weight-sorted holdings view would never surface that. The second was that scenario precedence is a real financial modeling decision, not just an implementation detail: naively summing an asset-specific shock and a sector shock that both target the same holding double-counts a single underlying risk exposure as if it were two independent ones — the same conceptual error DCF's `ScenarioAnalysis.md` warns against for mixing valuation-mechanics changes into a business-performance scenario, encountered again in a new domain.

## Engineering concepts learned

Splitting the engine into a resolver (which single rule governs a holding) and a calculator (what that rule does to its value) turned out to matter more than expected — precedence and overlap bugs and arithmetic/rounding bugs are genuinely different failure classes, and keeping them in separate pure modules with separate test files made both much faster to isolate while writing tests directly from the sprint brief's worked examples. The second was distinguishing "a rule lost to a more specific rule" (`overriddenRules`) from "a rule matched but couldn't be evaluated at all" (`unevaluableRules`, currently only a MARKET rule with unknown holding beta) — an edge case a first-pass implementation collapsed into one list, caught immediately by a test asserting the two should stay separate, since conflating them would hide a real data gap (missing beta data) behind what looks like an ordinary precedence outcome.

## Product decisions

The most consequential call was refusing to let historical volatility/beta/drawdown ever influence a scenario's shock value, even though the data is right there and would be easy to quietly blend in — enforced structurally, not just by convention: `historicalContext` is a separate top-level response key with no code path feeding it back into `resolver.js`'s rule matching. The second was excluding probability entirely — no "Bear Case: 20% likely" anywhere, even though users will naturally want to know which scenario to weight more heavily; Athena has no defensible statistical basis for such a number and stating one would misrepresent illustrative presets as calibrated forecasts. Scenario comparison reports "largest modeled impact" language, deliberately never "best"/"most dangerous" — the same neutral-register discipline Sprint 14 established for concentration/risk language, re-verified here against every new UI string before shipping.

## Scenario precedence methodology

Asset > Industry > Sector > Market > Portfolio-wide, most specific to least. Industry outranks Sector because Athena's `Company` model (Sprint 13) carries them as two independent free-text fields where industry is always the finer-grained label — more specific still wins. A holding matched by multiple rules is governed by exactly one (the highest-precedence evaluable one); every other matching rule is recorded, never silently dropped, so "which rule affected this holding, and what else would have applied" is always answerable from the API response (`research/engineering/ScenarioPrecedence.md`).

## Multi-factor scenario methodology

A scenario is a flat list of independent rules (`{targetType, target, shockPercent}`); the resolver evaluates every rule against every holding and keeps only the winner per holding per the precedence above — there is no sequential "apply rule 1, then rule 2" replay, and shocks from different rules targeting the same holding are never summed or multiplied together.

## Attribution

Two ratios per holding and per sector, deliberately kept as separate fields: Portfolio Impact (this holding's absolute change as a share of current total portfolio value) and Contribution to Scenario Impact (this holding's share of the scenario's total dollar change) — the latter computed against the scenario's net, signed total, so it can legitimately be negative or exceed 100% when holdings move in opposite directions, a correct property of attribution against a net total rather than a bug (`research/finance/ScenarioAttribution.md`).

## Bear/Base/Bull design

Six static, editable presets (`bear`, `base`, `bull`, `marketCorrection`, `technologySelloff`, `broadMarketStress`) in `portfolio.scenario.presets.js`, returned as deep copies so a caller mutating a loaded preset in the builder can never corrupt the canonical source. Every preset is labeled `"Hypothetical preset"` in the API response itself, not only in frontend copy, so the label survives regardless of which client consumes the endpoint.

## Historical context

Entirely reused from Sprint 14/15's existing `portfolioAnalyticsService.getPortfolioAnalytics()` (already cached, 5-minute TTL) — the scenario service extracts volatility/beta/max-drawdown/benchmark fields from that response and attaches them under a separate `historicalContext` key. No historical metric is recomputed in the scenario engine, and no historical value is ever read back into a rule's `shockPercent`.

## Why scenarios are not forecasts

The sprint's one non-negotiable framing rule: "if these assumptions occur, the modeled impact is X," never "this will happen." Enforced in the API response shape (assumptions block on every result), the frontend copy ("Hypothetical - not a forecast" in the result header), and every preset/documentation string.

## Why probabilities were excluded

No principled, defensible basis exists for assigning a likelihood to a hypothetical shock value — doing so would dress up an illustrative assumption as a calibrated statistical claim. Sprint 16 explicitly defers probability modeling rather than fabricate one (`research/product/AdvancedScenarioProductDesign.md` Section 9, `research/finance/PortfolioStressTesting.md` Section 5).

## Why AI does not generate assumptions

An AI-suggested shock value is functionally a forecast generated by a system with no principled basis for it. `research/engineering/GroundedScenarioExplanation.md` documents the (unimplemented) future explanation layer's boundary precisely: it may only restate already-computed numbers from a scenario's structured response, never compute or suggest a new one.

## Why scenarios are not persisted

No `Scenario` collection — a run/compare request is computed and returned in one pass, nothing written to the database. Keeps this sprint's infrastructure matched to what's actually been validated (whether users find hypothetical scenario analysis useful at all) before investing in persistence, sharing, or scheduled re-runs of something whose fit within Athena isn't yet established.

## Challenges

The single hardest problem was one this sprint didn't expect going in: discovering Sprint 15's scenario engine didn't actually exist, requiring the single-shock foundation (which the brief treated as "already built, just extend it") to be designed and built from scratch under the same precedence/attribution discipline as the harder multi-factor requirement, rather than being a quick warm-up before the real work. The second was the `overriddenRules`/`unevaluableRules` split (see "Engineering concepts learned") — caught by a test that initially failed for the right reason, forcing a genuine design correction rather than a workaround.

## Limitations

No cross-holding correlation modeling — a Technology selloff dragging down an unrelated holding isn't captured unless the user writes an explicit rule for it. No path dependency — a scenario is an instantaneous snapshot shock, not a simulated decline-and-recovery. Sector/industry rule matching is an exact string match against Yahoo-sourced classification; a portfolio using a different taxonomy or with unclassified holdings will see those specific rules simply not apply to the mismatched holdings. Sensitivity analysis is deliberately one-dimensional (one rule flexed at a time) per the brief's "no giant matrix" constraint.

## Future improvements

AI-generated scenario explanation, using the grounding design already written in `GroundedScenarioExplanation.md`. Saved/named scenario templates and scenario-triggered portfolio monitoring alerts, once usage data justifies the persistence infrastructure currently deferred. A confidence/coverage indicator on scenario results proportional to how much of the portfolio's value has a known beta or sector classification, similar to Sprint 14's `betaCoveragePercent`. Multi-dimensional sensitivity (flexing two rules across a grid simultaneously), if single-rule sensitivity proves insufficient in practice.

## Finance interview questions

1. **"Why does Athena's scenario engine only apply one rule per holding, even when several rules technically match it?"** — Because two rules matching the same holding are both claims about that holding's price move at the same moment, not independent effects — summing or multiplying them would double-count a single risk exposure. The most specific rule (Asset > Industry > Sector > Market > Portfolio-wide) is treated as the more informed claim and wins outright.
2. **"A holding is 2% of the portfolio by weight but explains 40% of a scenario's total loss. Is that a bug?"** — No — that's exactly what Contribution to Scenario Impact is designed to surface: a small position that happens to receive the scenario's harshest shock can dominate the loss's composition without being a large position by weight.
3. **"Why can a holding's contribution to scenario impact be negative or exceed 100%?"** — It's computed against the scenario's net, signed total change. When some holdings gain and others lose in the same scenario, the net total shrinks, and an individual holding's signed contribution against that smaller net can mathematically exceed 100% or flip sign — a known property of attribution against a net total, not an error.
4. **"How does a Market shock translate into a per-holding shock?"** — `holding.beta × rule.shockPercent`, reusing Sprint 14's exact Portfolio Beta methodology (weighted average of Yahoo-supplied betas) rather than inventing a new one. A holding with no known beta falls through to a lower-precedence rule instead of being silently assigned 0%.
5. **"Why isn't a Bear Case preset's -15% market shock derived from this portfolio's actual historical volatility?"** — Because doing so would silently replace the user's ability to state their own hypothesis with a data-derived one — the sprint's core principle is that historical data is context, never authoritative over a user-entered or preset assumption.
6. **"What's the difference between Athena's scenario stress testing and a bank's regulatory stress test (e.g. CCAR)?"** — A regulatory stress test uses prescribed, statistically calibrated macro paths set by regulators. Athena's presets are transparent, user-editable illustrative starting points with no calibration claim — useful for the same kind of exercise, but explicitly not a compliance-grade artifact.
7. **"Why does Athena show historical max drawdown next to a scenario result instead of using it to validate the scenario's severity?"** — Because Athena has no principled basis to declare a user's chosen shock "realistic" or "extreme" — showing the historical figure lets the reader make that judgment themselves, without Athena asserting an opinion it can't defend.
8. **"If Technology and Financial Services both show a positive Contribution to Impact in the same Bull scenario, do they sum to 100%?"** — Only if no other sector moved in the opposite direction and every other sector's total change is exactly offset elsewhere — contributions sum to 100% of the *net* total, not necessarily an intuitive 100% split across sectors when signs differ across the portfolio.
9. **"What does sensitivity analysis add beyond a single scenario run?"** — It shows the *slope* around one specific assumption — how much the portfolio's outcome depends on getting that one number right, by holding every other rule fixed and varying only the targeted one across a small range.
10. **"Is a portfolio that survives Athena's Broad Market Stress preset proven to be low-risk?"** — No — it only shows the modeled consequence of that one specific, editable hypothetical. A different combination of shocks, or a shock to a factor the preset doesn't cover, could produce a very different result.

## Product Management interview questions

1. **"What's the core product question Sprint 16 answers, and how does it differ from Sprint 15's?"** — Sprint 15 (as actually delivered) answers "what did I actually hold and how has it performed historically." Sprint 16 answers "how would my portfolio behave under multiple realistic hypothetical scenarios, and which holdings or sectors drive the impact" — forward-looking and hypothetical rather than backward-looking and historical.
2. **"Why does Athena refuse to attach a probability to Bear/Base/Bull?"** — Because doing so would misrepresent an illustrative, editable starting convention as a statistically calibrated forecast Athena has no defensible basis to make — the same discipline that keeps every scenario framed as conditional ("if X, then Y"), never predictive.
3. **"Why is scenario persistence deferred to a future sprint instead of built now?"** — Because it's infrastructure investment ahead of validated need — the sprint prioritizes learning whether users find running and comparing hypothetical scenarios useful at all before building saving, sharing, or scheduled re-runs of something whose fit isn't yet established.
4. **"Why must every scenario response include a visible assumptions block rather than relying on the UI copy alone?"** — Because the assumptions (rules, portfolio value, beta used, methodology notes) are what make a number interpretable rather than misleading — burying them in a tooltip, or omitting them from the API response entirely, would let any other consumer of the API present the number without its necessary context.
5. **"Why does scenario comparison avoid ranking scenarios as 'best' or 'worst'?"** — Because that would require Athena to assert an opinion about which outcome is more likely or more desirable for a specific user — information Athena doesn't have (risk tolerance, goals, time horizon) and shouldn't assume. The comparison reports raw, comparable numbers; interpreting them is left to the reader.
6. **"How does this sprint complement Sprint 14's Portfolio Analytics rather than duplicate it?"** — Sprint 14 is backward-looking and structurally under-samples rare severe events by definition (they're rare in any historical window). Sprint 16 is forward-looking and hypothetical, filling exactly that gap — and the two are kept visually separate on the page so a reader always knows which kind of claim they're looking at.
7. **"What's the biggest unresolved product risk in this feature as shipped?"** — Whether users actually internalize the precedence model (only one rule ever applies per holding) without reading documentation — the rule-chip UI and explanatory footnote are the current mitigation, unverified with real users (`AdvancedScenarioProductDesign.md` Section 12).
8. **"Why does Athena show Contribution to Impact as a separate column from Portfolio Impact instead of picking one?"** — Because they answer genuinely different questions a user might want either or both of — how much did this holding move the whole portfolio, versus what share of the total swing came from here — and collapsing them into one number would force a decision the product has no reason to make for the user.
9. **"How would you validate whether the weight-vs-contribution distinction is actually understood by users?"** — Test whether users can correctly predict which holding "caused" most of a scenario's loss before seeing the attribution table, then check whether their intuition (likely weight-based) diverges from the actual contribution numbers — the gap is the direct measure of whether the distinction needs clearer UI treatment.
10. **"If this sprint had half the engineering time, what would you cut first?"** — Sensitivity analysis — it's a genuinely separate feature layered on top of an already-complete scenario/comparison engine, and the core Bear/Base/Bull, multi-factor, and comparison functionality remains a coherent, complete-feeling product without it.

## Engineering / AI interview questions

1. **"Walk through why the scenario engine is split into a resolver and a calculator instead of one module."** — They solve different problems with different failure modes: "which single rule governs this holding" (matching/precedence, a combinatorial correctness problem) versus "what does that shock do to value and how does it roll up to the portfolio" (arithmetic/aggregation). Splitting them meant precedence bugs and rounding bugs surfaced in separate, more targeted test files instead of one large one, and made an actual design bug (the `overriddenRules`/`unevaluableRules` conflation) easy to isolate and fix.
2. **"Why does `/compare` fetch portfolio/company/beta context exactly once instead of once per scenario?"** — Because that data doesn't vary between scenarios in the same comparison — only the rules do. Fetching it once and running the cheap, pure calculation N times against the shared snapshot is both faster and guarantees every scenario in the comparison was evaluated against identical portfolio data — verified directly in tests via mock call-count assertions.
3. **"How does Athena guarantee the sensitivity table's numbers agree with what a full `/run` call for the same shock value would produce?"** — Sensitivity re-runs the exact same pure `resolveScenario()` + `calculateScenarioImpact()` pipeline `/run` uses, once per requested shock value, over the same already-fetched context — there's no separate sensitivity-specific calculation path that could silently drift out of sync.
4. **"Why does a MARKET rule with unknown beta fall through to a lower-precedence rule instead of just being skipped?"** — Because the holding still needs *some* outcome if a broader rule (like PORTFOLIO) also matches it — skipping it entirely would silently leave that holding unaffected even when the user clearly intended some rule to apply. The engine keeps searching down the precedence order for the next rule it *can* actually evaluate, rather than stopping at the first one that merely matches.
5. **"If Athena adds AI-generated scenario explanation later, what's the one architectural guarantee that must never be violated?"** — The AI must never be in the calculation path — every number it references must already exist in the structured JSON response before the AI is invoked, and its output should be mechanically checkable against that input (every numeric claim traceable back to a value Athena already computed). The moment an AI is allowed to compute or suggest a number instead of only rephrasing one, the entire "deterministic, testable, LLM-independent engine" guarantee this sprint (and the whole scenario feature) depends on is broken.
