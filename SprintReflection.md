# Sprint 14 Reflection — Advanced Portfolio Analytics & Risk

## What was built

A portfolio-level analytics and risk engine answering "how is my portfolio performing and what risks does its current composition create?" — the question Sprint 9's cost-basis tracking never attempted. `backend/portfolio/portfolio.analytics.{calculator,risk,exposure,correlation,service,validator,controller,routes}.js` (four pure calculation modules plus orchestration, matching the existing `portfolio.calculator.js`/`dcf.formulas.js`/`comps.formulas.js` split), exposed as a single `GET /api/portfolio/analytics` endpoint returning performance, risk, concentration, sector/industry exposure, holdings, correlation, and a visible assumptions block. A new Portfolio Analytics section (`frontend/src/components/portfolio/`: `PerformanceSection`, `RiskSection`, `ExposureSection`, `ConcentrationSection`, `CorrelationMatrix`, `AssumptionsPanel`) appended below Sprint 9's existing holdings table in `Portfolio.jsx` — the original page is otherwise untouched. 64 new backend tests (23 calculator, 4 risk, 9 exposure, 8 correlation, 6 validator, 10 service, 6 routes) joined the pre-existing 835-test backend suite with zero regressions (899 total, confirmed by repeated full-suite runs). No new frontend tests were added, consistent with this codebase's existing convention (no frontend component tests exist anywhere in the repo, for any sprint); the frontend was instead verified via `eslint` (clean) and a production `vite build` (clean) after every change. Fourteen new/extended documentation files across `research/finance/`, `research/engineering/`, and `research/product/`.

## Finance concepts learned

The clearest lesson was that "portfolio return" and "portfolio performance return" are not one number wearing two names — they answer genuinely different questions and can legitimately disagree. Sprint 9's `unrealizedReturnPercent` reflects what was *actually paid* for each lot; the new `periodReturnPercent` reflects what *today's mix* would have earned over a fixed historical window, entirely independent of when anything was actually purchased. Collapsing them into one field would have quietly hidden which question was being answered. The second lesson was that a risk metric's usefulness depends entirely on what it's silent about — Beta says nothing about total volatility, HHI says nothing about correlation, Correlation says nothing about sector overlap — which is exactly why `PortfolioDiversification.md` argues against collapsing them into one composite "diversification score": each lens catches a different failure mode the others miss.

## Engineering concepts learned

The most consequential engineering decision was choosing portfolio beta as a weighted average of each holding's own provider-supplied beta, rather than a regression of the portfolio's own historical returns against a benchmark's. This wasn't just a simpler implementation — it structurally decouples Beta from the benchmark ever resolving successfully at all, which mattered once the benchmark itself became something that could legitimately fail (an unresolvable ticker, a provider outage) without being allowed to take down the whole analytics response. The second was historical data alignment: naively zipping two tickers' price-bar arrays by index silently produces wrong pairings the moment either ticker has a gap, so every historical calculation aligns by trading *date* through a `Map`, with an explicit minimum-coverage threshold (50% of portfolio weight) before a given day counts as usable — see `HistoricalDataAlignment.md`.

## Product decisions

The single most consequential product call, made explicit and unprompted in the sprint's opening question, was picking the default benchmark: defaulting unconditionally to SPY would have made Beta and the benchmark performance comparison meaningless for a portfolio composed mostly of Indian (NSE/BSE) holdings. Rather than leave this as a silent gap, the benchmark now auto-selects from the exchange holding the largest share of portfolio value (`NSE`/`BSE` → `NIFTYBEES.NS`, else → `SPY`), fully overridable via `?benchmark=`. Every risk and concentration number is presented in the sprint's required neutral register throughout — no "too concentrated," no "consider diversifying" — verified by re-reading every new UI string against that constraint before shipping (see `PortfolioRiskProductDesign.md` Q4/Q6). Assumptions (analysis window, benchmark, risk-free rate, historical-weight methodology) are rendered as their own always-visible panel rather than tooltips, on the reasoning that a number's meaning changes depending on whether the reader knows it's an estimate.

## Historical weight methodology

Athena's `Holding` model stores current lots only — no transaction ledger, no daily snapshot of past composition. Every historical metric (volatility, Sharpe, drawdown, period return, correlation) is therefore built by applying **today's** weights backward over each holding's own historical daily price returns (`Rp_t = Σ wi(today) × Ri,t`), not a reconstruction of what the portfolio actually held or was worth on any past date. This is stated once, centrally, in `assumptions.historicalWeightMethodology` on every API response and in `PortfolioCalculationAssumptions.md`, rather than re-explained per metric. See that document's "Alternatives considered" for why refusing to compute anything (the other defensible option) was rejected in favor of a disclosed estimate.

## Benchmark decisions

Configurable via a `benchmark` query parameter, never hard-coded through the calculation layer. With no override, the default is auto-selected from portfolio composition (see "Product decisions" above) rather than a single fixed assumption. The benchmark is resolved as an ordinary tradeable security (SPY, NIFTYBEES.NS) rather than a raw index symbol (`^GSPC`) specifically so it reuses `companyService.resolveTicker`'s existing auto-import and `market.service`'s existing `MarketHistory` caching with zero new provider code — the same reasoning `riskFreeRateProvider.js` already established for why `^TNX` (a genuine index, not a tradeable security) needed to bypass `market.service` entirely. Critically, Beta does not depend on the benchmark resolving at all (see "Engineering concepts learned") — a benchmark failure only removes the optional benchmark-comparison context field.

## Risk-free rate decisions

Reused directly from Sprint 6: `valuation/providers/riskFreeRate.provider.js`'s live 10-Year US Treasury yield (`^TNX`), already built for DCF's CAPM cost-of-equity calculation. When the live fetch fails, Sharpe Ratio falls back to a documented illustrative constant (`ILLUSTRATIVE_RISK_FREE_RATE = 0.04`) rather than going permanently blank — a deliberate departure from DCF's own fallback behavior (DCF just labels the field "unavailable" and lets the user type a value in, since it's an interactive form; Sharpe Ratio has no equivalent form, so leaving it blank whenever the Treasury feed hiccups would silently degrade a read-only page with no way for the user to supply a substitute). Every response states which source was actually used (`"market"` vs. `"illustrative_default"`) — never presented as live when it isn't.

## Concentration methodology

Extends Sprint 9's existing `topHoldingWeightPercent`/`top3WeightPercent` (unchanged, still on `GET /api/portfolio`) with `top5WeightPercent` and HHI, computed independently in the new analytics layer from the same ticker-grouped positions rather than modifying Sprint 9's calculator. HHI uses the antitrust-standard percentage-point scale (0–10,000), not the 0–1 decimal scale, specifically because it produces round, commonly-cited numbers rather than small decimals requiring a mental conversion — see `HHI.md`.

## Correlation methodology

Each pair of holdings is correlated over its own overlapping trading dates, deliberately not the shorter whole-portfolio-aligned date set used for volatility — truncating an older pair down to a third, newer holding's shorter history would throw away real, usable data for no reason. A 20-observation minimum-overlap floor prevents a coefficient from being reported on too few points to be meaningful; a constant (zero-variance) series reports `null`, never a fabricated 0.

## Caching decisions

Keyed by `userId:window:benchmark:portfolioVersion`, where `portfolioVersion` is a cheap deterministic hash of the user's raw holdings (not the expensive computed output) — so editing a holding busts the cache the instant it happens, rather than waiting out a fixed TTL, while a 5-minute TTL on top bounds staleness of the underlying market data. Verified in tests: two different users never share a cache entry even with byte-identical holdings, and a shares/price/date edit forces recomputation on the very next request. Documented in `AnalyticsCaching.md` as a real, unresolved trade-off: stale cache entries (from a holdings composition the user has since changed) are never actively evicted, only left permanently unreachable — acceptable given personal-portfolio edit frequency, but not actually bounded by design.

## What was intentionally deferred

AI-generated explanation of portfolio analytics — explicitly optional per the brief; the design constraints it would need to follow (structured input only, no AI-computed numbers, no recommendations) are written up in `GroundedPortfolioExplanation.md` rather than left unaddressed. Portfolio rebalancing/optimization — the sprint brief explicitly excludes it, and `PortfolioRiskProductDesign.md` Q7 explains why prescribing changes requires information (risk tolerance, goals) Athena doesn't collect. Transaction-aware historical analytics (a real historical-holdings snapshot replacing the current-weights approximation) — named as the first thing worth building next in `PortfolioCalculationAssumptions.md`, deliberately out of scope this sprint per the brief's REBALANCING section. Multiple analysis windows beyond what `market.service` already supports natively — all five (1m/3m/6m/1y/5y) were exposed since the underlying data layer already handles them uniformly at no extra engineering cost, rather than being artificially restricted to 1Y only.

## Challenges

The benchmark-default decision (see "Product decisions") was the sprint's sharpest judgment call, surfaced directly by the user rather than caught in initial design — the first-draft plan (SPY unconditionally) would have shipped a benchmark that's actively misleading for a real, plausible class of Athena users (Indian-market-heavy portfolios), not just imprecise. The second challenge was resisting the temptation to compute portfolio beta via regression against the benchmark, which is the textbook "more rigorous" approach — rejected specifically because it would have made Beta depend on the benchmark's historical data resolving successfully, coupling two things (a holding-level risk statistic and an optional comparison ticker) that don't need to depend on each other.

## Future improvements

A transaction-aware analytics engine using real historical holdings snapshots (see `PortfolioCalculationAssumptions.md`), removing the current-weights approximation for the period after a snapshot begins. A confidence indicator on historical metrics proportional to `observedTradingDays` relative to the requested window, rather than a binary available/unavailable. The optional AI explanation layer, using the grounding design already written in `GroundedPortfolioExplanation.md`. A periodic sweep or LRU cap on the analytics cache, if the unbounded (though slow-growing) `Map` documented in `AnalyticsCaching.md` ever becomes a measured problem rather than a theoretical one.

## Finance interview questions

1. **"Why does Athena report two different portfolio return numbers instead of one?"** — `unrealizedReturnPercent` (Sprint 9) reflects actual cost basis vs. current value; `periodReturnPercent` (Sprint 14) reflects an estimate of how *today's* holdings would have performed over a historical window. They answer different questions and can legitimately disagree — merging them would hide which one a reader is looking at.
2. **"Why does Athena use √252 to annualize daily volatility instead of just multiplying by 252?"** — Variance scales linearly with time; standard deviation is variance's square root, so it scales with √time. Multiplying the daily figure directly by 252 would overstate annual volatility by roughly 15.9x too much.
3. **"Why is portfolio beta computed as a weighted average of individual betas instead of a regression against the benchmark?"** — It reuses each holding's own already-computed, standard-methodology beta at zero extra API cost, and critically decouples Beta from the benchmark's historical data ever resolving successfully — a documented trade-off against the mixed-benchmark limitation this method carries for multi-market portfolios (`PortfolioBeta.md`).
4. **"A portfolio's Sharpe Ratio is negative. Does that mean the portfolio lost money?"** — Not necessarily — a negative Sharpe only means the portfolio's return was below the risk-free rate over the window; the portfolio could still have a positive absolute return, just smaller than what a risk-free asset would have paid.
5. **"Why does zero volatility return `null` for Sharpe Ratio instead of `Infinity`?"** — An infinite Sharpe Ratio isn't a real, interpretable risk-adjusted return, it's a division-by-zero artifact — reporting it as unavailable is more honest than presenting a number that looks like an extraordinary result.
6. **"What does Maximum Drawdown's 'no recovery observed' actually tell you?"** — Only that the series didn't climb back above its pre-drawdown peak *before the analysis window ended* — not that the portfolio is still at its lowest point today. It's frequently just an artifact of a short window ending mid-decline.
7. **"Why does HHI use a 0–10,000 scale instead of 0–1?"** — The antitrust-standard convention (percentage-point weights squared and summed) produces round, commonly-cited thresholds; a 0–1 decimal scale would require an extra mental conversion for the same information.
8. **"Two portfolios both show low top-holding concentration. Are they equally diversified?"** — Not necessarily — concentration only measures position-size distribution. Five equally-weighted holdings in the same sector would pass a concentration check while still being an effective single-sector bet, which is why Athena also reports Exposure and Correlation as separate, independent signals rather than one composite score.
9. **"Why does Athena's correlation calculation use each pair's own overlapping dates instead of the whole portfolio's aligned date set?"** — Because the portfolio-wide aligned set is deliberately shortened by whichever holding has the least history; truncating two long-history tickers down to a third, newer one's shorter overlap when correlating just the first two would throw away real, usable data for no reason.
10. **"Is Athena's historical portfolio volatility a forecast of future volatility?"** — No — it's backward-looking, and built on an additional estimate on top of that (today's weights applied to historical returns, not the portfolio's real historical composition). Athena states both limitations explicitly rather than implying predictive power.

## Product Management interview questions

1. **"What's the core product question Sprint 14 answers, and how does it differ from Sprint 9?"** — Sprint 9 answers "what do I own and how has each position done." Sprint 14 answers "how does my portfolio behave as a system, and what risk does its current shape create" — a question no combination of per-holding numbers can answer on their own.
2. **"Why does the default benchmark change based on portfolio composition instead of always being SPY?"** — Because an Indian-market-heavy portfolio's Beta and benchmark-comparison numbers would be actively misleading against a US index — the auto-detection (majority-exchange-by-value → matching benchmark ETF) exists specifically so users who never think to override a benchmark parameter still get a meaningful default.
3. **"Why is concentration/risk language kept strictly neutral, even for an obviously concentrated portfolio?"** — Because a concentrated position can be an entirely deliberate, legitimate strategy — Athena has no basis to know a specific user's conviction level or risk tolerance, so it reports the fact ("top holding is 40% of value") and stops there, never converting it into "you should diversify."
4. **"Why must the Assumptions panel be an always-visible section rather than a tooltip?"** — Because nearly every historical number on the page is an estimate (current weights applied backward), and a reader who doesn't know that will interpret a Sharpe Ratio or volatility figure as a stronger claim than Athena is actually making. A tooltip technically discloses it; a visible panel is what actually gets read.
5. **"Why is portfolio optimization explicitly out of scope this sprint?"** — Because prescribing portfolio changes requires information Athena doesn't have and shouldn't assume — risk tolerance, time horizon, tax situation, goals outside the app. Describing a portfolio's current characteristics is a well-scoped problem Athena can answer correctly with the data it has; prescribing changes is a fundamentally different, much riskier one.
6. **"How does this sprint improve Athena's retention story, beyond Sprint 9's watchlist mechanic?"** — Risk metrics change as markets move and as holdings change, giving users a reason to check back beyond "did my return go up" — and Exposure/Concentration are designed to prompt click-through to a specific holding's Company Dashboard or Industry Intelligence page, extending Sprint 9's "funnel toward deeper tools" pattern.
7. **"What's the biggest open product risk in this sprint as shipped?"** — Whether Sharpe Ratio and Beta are actually understood by users without a finance background — they're the two most jargon-dense metrics shipped, and it's genuinely unverified whether they need companion explanatory copy or a glossary link (`PortfolioRiskProductDesign.md` Q10).
8. **"Why doesn't Athena compute one single 0–100 'diversification score'?"** — Because it would force an arbitrary weighting between three conceptually different signals (concentration, exposure, correlation) that can disagree in informative ways — a low score could mean any of several different underlying problems, and collapsing them loses exactly the information a user would need to understand why.
9. **"How would you validate the current-weights historical approximation is an acceptable trade-off to users, not just to engineering?"** — Test whether users can correctly restate what "current-weight approximation" means after reading the Assumptions panel — the direct test of whether disclosure is actually landing, versus technically present but not understood.
10. **"If this sprint had half the engineering time, what would you cut first?"** — The correlation matrix — it's the metric requiring the most sophisticated audience to interpret usefully (per the expected-usage hypothesis in `PortfolioRiskProductDesign.md` Q9), and Performance/Risk/Exposure/Concentration remain a coherent, complete-feeling feature without it.

## Engineering / AI interview questions

1. **"Walk through why naive index-alignment of two tickers' price bars is a real, silent bug, not just a style preference."** — If ticker B is missing one bar mid-window (a provider gap), zipping by array index means every subsequent index pairing drifts out of calendar sync with ticker A — `barsA[500]` and `barsB[500]` may no longer represent the same actual date. Every portfolio return computed from that point on silently combines two different days' returns as if they were one, with no error thrown.
2. **"Why does the analytics cache key on a hash of raw holdings (`portfolioVersion`) instead of just a short TTL?"** — Because a short TTL alone means a user who just edited a holding sees stale numbers until it expires — worse for a page whose entire point is "reflect what I currently hold." Baking holdings into the key means an edit invalidates the cache the instant it happens, at the cost of one extra cheap indexed query per request.
3. **"Every calculator function in this sprint returns `null` instead of `NaN`/`Infinity` on bad input. Why does that matter specifically for a risk-analytics feature?"** — Because a technically-computable-but-meaningless value (an infinite Sharpe Ratio, a beta silently defaulted to 0) looks like a real result and carries no visual signal not to trust it — worse than an obvious crash. `null` plus a stated reason preserves the distinction between "this is a real number" and "this couldn't be computed" all the way to the UI.
4. **"Why doesn't portfolio Beta depend on the benchmark ticker resolving successfully?"** — Because the method chosen (weighted average of each holding's own provider-supplied beta) never touches the benchmark's own price history at all — the benchmark is only used to label what's being compared against and to fetch an optional comparison return. A benchmark resolution failure degrades only that optional context field, never the core Beta calculation.
5. **"If Athena later adds a true batch historical-price provider endpoint, what changes in the analytics engine?"** — Only `portfolio.analytics.service.js`'s fetch step (`Promise.all` per-ticker calls → one batch call) — none of the four calculator modules (`calculator.js`/`risk.js`/`exposure.js`/`correlation.js`) know or care how their input data was fetched, they only operate on already-fetched prices, weights, and classifications.
