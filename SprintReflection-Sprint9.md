# Sprint 9 Reflection — Portfolio & Watchlist Intelligence

*Continuing the `SprintReflection-SprintN.md` convention Sprints 2, 4, 5, 6, 7, and 8 use — see Sprint 6's reflection for the note on why the unsuffixed `SprintReflection.md` holds Sprint 3's reflection instead.*

## 1. What was built

Athena's first persistent user layer, end to end. A minimal identity module (`backend/identity/`) — an opaque bearer token, hashed before storage, resolved server-side on every request via `identity.middleware.js`, deliberately *not* a full login system. A Watchlist module (`backend/watchlist/`): one embedded-array document per user, a `GET/POST /api/watchlist` and `DELETE /api/watchlist/:ticker` API that fans out to four existing engines (market, analysis, valuation, and an illustrative-DCF helper reusing Sprint 8's own credit-spread constants) per row, and a frontend page with add/remove/search/empty states. A Portfolio module (`backend/portfolio/`): one document per purchase lot, a pure calculation engine (`portfolio.calculator.js`) computing cost basis, current value, gain/loss, value-weighted return, ticker-grouped positions, and concentration, a full CRUD API with ownership-scoped queries, and a frontend page with summary cards, an intelligence panel, a holdings table, and an add/edit modal. Change detection (`watchlistInsights.service.js` + `WatchlistSnapshot`): a `(userId, ticker)`-scoped "last observed metrics" record compared on an explicit `GET /api/watchlist/insights` checkpoint, generating human-readable diffs for five deliberately-chosen tracked metrics. 91 new backend tests (9 identity, 19 watchlist CRUD, 50 portfolio, 13 change detection) joined the pre-existing 365-test backend suite, all of which stayed green throughout (456 total, confirmed by repeated full-suite runs across the sprint); 72 pre-existing frontend tests stayed green with no new frontend tests added this sprint (see Section 10). Every Sprint 1–8 route, service, and model was left untouched except three additive lines in `server.js` (new route mounts, widened CORS methods) and one additive prop on the shared `EmptyState` component.

## 2. Finance concepts learned

The sharpest lesson was that "portfolio return" has an easy-to-state, easy-to-get-wrong answer: averaging each holding's individual return % feels intuitive and is measurably incorrect the moment position sizes differ. Working through a concrete live example made this vivid rather than theoretical — a $1,500 AAPL position (blended +51.1% across two lots) and a $1,200 MSFT position (+23.1%) produce a naive average of 37.1%, but the actual value-weighted portfolio return, verified against real numbers, was 43.12%. The second lesson was about the honest handling of "unknown": a zero cost basis (gifted shares) makes return % mathematically undefined, not infinite, and a missing live price makes a holding's value *unknown*, not *zero* — both distinctions matter because the wrong choice (returning `Infinity`, or silently treating an unpriced holding as worthless) would corrupt every aggregate built on top of it, not just look cosmetically wrong in isolation.

## 3. Engineering concepts learned

The most consequential lesson was catching a design mistake before it shipped, not after: the first plan for change-detection snapshots was a single record shared per *ticker*, on the reasoning that many users tracking the same popular stock shouldn't each need their own copy of the same five numbers. Tracing through a concrete scenario — User B's visit updates the shared snapshot, so User A's next visit compares against a value A never actually saw — surfaced a real, silent correctness bug (a change would be invisible to A, not merely wrong) before a single line of the snapshot model was written. The fix (scope by `(userId, ticker)` together) cost a small amount of storage duplication in exchange for a class of bug becoming structurally impossible rather than something to hope doesn't happen. The second lesson was noticing that two data-model decisions that look inconsistent on the surface — Watchlist as one embedded-array document per user, Portfolio as one top-level document per holding — are actually both correct, for opposite reasons: a watchlist entry has no independent lifecycle (present or absent, nothing to edit), while a holding needs stable per-lot identity for independent CRUD. Reaching for the same shape for both would have optimized one feature at the other's expense.

## 4. Product decisions

Keeping Watchlist and Portfolio as genuinely separate concepts — not a shared "companies I care about" list with an `owned` flag — was the sprint's foundational call, made explicit in the sprint brief and reinforced by tracing through the concrete failure mode it prevents (a user reading a watched stock's paper "gain since added" the same way they'd read an actual investment gain). The minimal-identity-over-full-auth decision was the second major call, confirmed with the user before any identity code was written specifically because it's hard to walk back cleanly once Watchlist/Portfolio data references it. A smaller but real mid-implementation decision: surfacing `currentPrice` and `currency` per portfolio holding (not originally planned) after recognizing that Athena already supports non-USD tickers, and that summing raw current values across currencies into one portfolio total would be silently wrong without at least being honest about which currency each row is actually in.

## 5. User retention considerations

The entire premise of this sprint is a retention mechanic Sprints 1–8 structurally couldn't have: a stateless research tool has no reason to pull a user back, since the answer to "what do I need to know about AAPL" doesn't change meaningfully day to day. A watchlist manufactures an open loop — once a ticker is saved, "did anything change" has a potentially different answer on every visit, and Athena becomes the place that answer lives. Two design choices protect that loop from being wasted: change detection is an explicit "Check What's Changed" action, not an automatic side effect of loading the page, specifically because auto-firing it on every visit would silently consume the comparison before the user ever saw the result — and every watchlist/portfolio row links outward (to the full Company Dashboard, to an AI research report, to the other feature via the cross-link button), so the feature funnels toward Athena's deeper tools rather than becoming a shallow destination that substitutes for them.

## 6. Data modeling decisions

Two deliberately different shapes for structurally different problems, both explained in depth in `WatchlistArchitecture.md` and `PortfolioDataModel.md`: Watchlist as one per-user document with an embedded `companies` array (no per-entry mutation needed, so no reason for per-entry identity), Portfolio as one top-level `Holding` document per purchase lot (independent shares/price/date edits need a stable, individually-addressable id). Neither sprint-brief-suggested wrapper collection (`Portfolio`, multi-list `Watchlist`) was built, following the instruction to treat suggested schemas as examples and avoid redundant collections where the existing data already answers the question — "a user's portfolio" is fully defined as `Holding.find({userId})`, no wrapper needed. `WatchlistSnapshot` got its own collection specifically because, unlike a watchlist entry, a "last observed metrics" record genuinely does need independent per-`(user, ticker)` storage — the one case this sprint where a separate collection was the right call for Watchlist-adjacent data.

## 7. Security decisions

Every user-specific query in both new modules is scoped by `userId` resolved server-side from a hashed bearer token — never read from a client-supplied field anywhere. Portfolio's ownership check is folded directly into the query itself (`Holding.findOneAndUpdate({_id: holdingId, userId}, ...)`), so a guessed or enumerated id belonging to another user matches nothing and returns an identical 404 to "doesn't exist," never leaking which case occurred. This was verified live against the running application with two real, independently-minted tokens, not just asserted in mocked unit tests: User B's `PUT`/`DELETE` against User A's real holding both returned 404 with zero mutation, and User A's and User B's watchlists never showed each other's tickers even when both users added different tickers concurrently. `requireIdentity` is mounted only on the two new routers, never globally, so every Sprint 1–8 route's security posture (or lack thereof — none of them ever needed auth) is completely unchanged.

## 8. Performance decisions

No new caching infrastructure was introduced — no Redis, no new in-memory layer — a deliberate decision documented in `UserScopedCaching.md` and `BatchDataFetching.md` rather than an oversight. Both Watchlist and Portfolio dedupe tickers before fetching live prices (a user with three lots of the same stock costs one price lookup, not three) and fetch in parallel via `Promise.all` rather than a serial loop, verified directly in tests and live (a 3-lot, 2-ticker portfolio triggered exactly 2 `getCurrentMarketData` calls). A true batch provider endpoint (`getQuotes(tickers[])` in one HTTP call) was considered and explicitly deferred — no such method exists anywhere in the provider layer today, and building one across both Yahoo and TwelveData is a bigger lift than justified by the tens-of-tickers list sizes a personal watchlist or portfolio actually has.

## 9. Trade-offs

**Minimal identity vs. real accounts.** No password, no cross-device login, no recovery if `localStorage` is cleared — an explicit, user-confirmed scope boundary, not a corner cut silently. **Storage duplication vs. correctness in `WatchlistSnapshot`.** Scoping snapshots per-user rather than sharing them per-ticker means near-identical rows for popular tickers across many users — accepted deliberately after finding the correctness bug the shared version would have caused (Section 3). **Parallel-per-ticker fetching vs. a real batch endpoint.** Solves the actual problem (redundant duplicate calls) without the cost of new provider-interface work — a documented, not permanent, scope boundary. **Watchlist row latency vs. richness.** A fully enriched watchlist row costs roughly four external/internal calls (quote, performance, analysis, illustrative DCF) — verified live at ~3.5 seconds for a single fresh row — acceptable for a page a user checks periodically, not instantly, but a real cost that would need addressing (background pre-computation, more aggressive caching) if watchlist sizes or check-in frequency grew substantially.

## 10. What was intentionally NOT built

Full username/password authentication, cross-device sync, or account recovery — deferred to a future "real accounts" sprint per the approved design. Multiple named watchlists per user — the schema leaves room (`name` field, relaxable unique index) but the UI/API for it wasn't built since the user story only ever describes one list. Multi-currency portfolio aggregation (FX-normalized totals) — flagged as a real, documented limitation rather than silently handled or silently ignored. A true batch market-data provider endpoint — deferred per Section 8. Sharpe Ratio, Beta, VaR, or any CAPM-based portfolio risk analysis — explicitly out of scope per the sprint brief; concentration (value-weight only) is the only risk metric this sprint implements. Automatic report generation for every watchlist company — the AI Research link is manual and on-demand, reusing Sprint 8's existing "Generate" button rather than triggering LLM calls for companies a user hasn't asked about. New frontend unit tests for `Watchlist.jsx`/`Portfolio.jsx` — verification for these pages relied on live end-to-end runs against the real dev stack (documented throughout this sprint's build) plus the existing `npm run lint`/`npm run build`/`vitest run` suite staying green, rather than new component-level tests; this is a real gap worth closing with more time (see Section 11).

## 11. What would be improved with more time

Component-level frontend tests for `Watchlist.jsx` and `Portfolio.jsx` (Section 10) — the live E2E verification this sprint relied on is strong evidence of correctness at a point in time but doesn't guard against regression the way `AIResearch.test.jsx` already does for Sprint 8's page. A real batch quote endpoint, once list sizes or traffic actually justify the provider-layer investment (Section 8). Multi-currency portfolio support (FX-normalized totals), once a live exchange-rate data source exists to make it trustworthy rather than another silent-precision-loss risk. Instrumenting the usage metrics proposed in `WatchlistAndPortfolioProductDesign.md` Section 10 (return-visit cadence, "Check What's Changed" repeat-usage rate, cross-feature funnel from Watchlist to Portfolio) — currently working hypotheses, not measured reality. Real accounts (password or OAuth-based), building on top of — not replacing — the current token-resolution architecture, since `identity.middleware.js`'s "resolve a credential to a userId server-side" shape doesn't need to change, only how the credential itself is issued.

## 12. Product Management interview questions

**Q1: Why introduce a persistent user layer in Sprint 9 and not earlier?**
A: Because it wasn't needed earlier — every prior sprint answers a question fully satisfied within one visit ("what do I need to know about this company"), with nothing to remember between sessions. "What has changed since I last checked" is meaningless without a *before* to compare against, and that's the first genuinely new requirement for user-specific state (`WatchlistAndPortfolioProductDesign.md` Q1).

**Q2: Why are Watchlist and Portfolio separate features instead of one unified list with an "owned" flag?**
A: They represent different financial realities that feel similar but aren't — watching costs nothing and carries no stake; owning means real money is at risk. Merging them risks a user reading a watched stock's paper gain the same way they'd read an actual investment gain, reinforcing exactly the FOMO/hindsight-bias reactions a good financial product should help a user reason past, not amplify (`WatchlistVsPortfolio.md`).

**Q3: The sprint chose a minimal token-based identity system over real login. How do you defend that to a stakeholder who wants "proper" accounts?**
A: It correctly solves the problem this sprint actually has — isolating one anonymous browser's data from another's — without the cost and friction of a full login system for a first version. It's an explicit, documented trade-off with a clear boundary (no cross-device sync, no recovery), not a security shortcut disguised as something stronger, and real accounts can be layered on top of the same server-side identity-resolution architecture later without a rebuild.

**Q4: How would you decide what belongs on the Watchlist row versus the full Company Dashboard?**
A: Anything a user can act on in a few seconds of scanning belongs on the row (price, daily change, Health Score, 1Y return, P/E, DCF gap); anything that needs its own explanation to be useful doesn't. Every additional column taxes the "quick check-in" use case the whole feature is built around — past a certain density the list stops being scannable and just duplicates the dashboard worse (`WatchlistAndPortfolioProductDesign.md` Q5–Q6).

**Q5: Why is "Check What's Changed" an explicit button instead of automatically showing changes every time the page loads?**
A: Because each check is also the checkpoint that overwrites "last seen" — auto-firing it on every page load would silently consume the comparison before the user ever saw it, turning a valuable signal into one that only ever shows "nothing changed" after the very first visit.

**Q6: Why does Athena report "42% of portfolio value is concentrated in one holding" instead of advice like "you should diversify"?**
A: The sprint's explicit product principle: analytical observations, never recommendations. A concentrated position can be an entirely intentional, legitimate strategy — the product's job is to make the fact visible, not to make the decision for the user (`ConcentrationRisk.md`).

**Q7: What's the biggest product risk in Watchlist/Portfolio as shipped?**
A: That users don't return to check in — the entire retention thesis depends on the "what changed" loop actually being closed by real usage, and it's currently a working hypothesis, not measured behavior (Section 11). The mitigation is structural (an explicit, easy-to-find action) but the real test is whether people come back and click it.

**Q8: How would you measure whether this feature is succeeding?**
A: Return-visit cadence for users with an active watchlist/portfolio (the core retention signal), "Check What's Changed" repeat-usage rate (whether the explicit-checkpoint design is actually used more than once), and cross-navigation from a watchlist/portfolio row to the deeper dashboard or an AI report (evidence the feature funnels toward Athena's other tools rather than substituting for them) — see `WatchlistAndPortfolioProductDesign.md` Section 10.

**Q9: A user asks why Athena doesn't just tell them whether to buy more of their best-performing holding. How do you respond?**
A: The same boundary Sprint 6 and Sprint 8 already hold for DCF and AI reports, applied here: Athena surfaces facts (this holding is your best performer, it's 75% of your portfolio) and leaves the decision entirely to the user. A recommendation implies a certainty about the future none of Athena's analysis actually claims.

**Q10: What would you build next for this feature area given more time?**
A: I'd want the Section 11 usage metrics first, but my working hypothesis is real multi-device accounts — the current identity system's biggest known limitation is that a cleared browser means a lost watchlist, which directly undermines the retention loop this whole sprint is built around.

## 13. Engineering interview questions

**Q1: Walk through what happens when a user calls `GET /api/watchlist/insights` for the second time.**
A: `watchlistInsights.service.js`'s `getInsights` calls `watchlistService.getWatchlistWithMetrics(userId)` to get current values for the five tracked metrics per ticker, then for each one queries `WatchlistSnapshot.findOne({userId, ticker})`. If a prior snapshot exists, each metric is compared against its threshold (absolute for Health Score/CAGR/valuation gap, percent for price/P/E); any metric past its threshold produces a human-readable change entry. Regardless of what changed, the snapshot is then unconditionally overwritten with the current values via `findOneAndUpdate(..., {upsert: true})` — so the *next* call compares against what this call just showed the user, not against older data.

**Q2: Why is `WatchlistSnapshot` scoped by `(userId, ticker)` instead of just `ticker`?**
A: A shared snapshot was the original plan, rejected after tracing a concrete bug: if User B's visit updates a global snapshot, User A's next comparison runs against a value A never saw, silently hiding a real change from A. Per-user scoping trades a small amount of storage duplication (popular tickers get one snapshot row per tracking user, not one globally) for that bug being structurally impossible (`UserScopedCaching.md`).

**Q3: Portfolio and Watchlist use different Mongoose schema shapes for conceptually similar "a user has a list of tickers" data. Justify that.**
A: They're not actually the same problem. A watchlist entry has no independent lifecycle — present or absent, nothing to edit — so one per-user document with an embedded array is simplest and sufficient. A portfolio holding needs independent CRUD (edit shares/price/date on one specific lot) with a stable, individually-addressable id, which an embedded-subdocument update (positional/`arrayFilters` operators) makes meaningfully more complex than a plain top-level `findOneAndUpdate({_id, userId})` — so Portfolio uses one document per holding instead (`WatchlistArchitecture.md`, `PortfolioDataModel.md`).

**Q4: How does Athena avoid an N+1 query problem when fetching prices for a portfolio with multiple lots of the same stock?**
A: `portfolio.service.js`'s `fetchQuotesByTicker` dedupes tickers through a `Set` before fetching, then fans out with `Promise.all`, building a `Map` the enrichment step looks up from — a 3-lot, 2-unique-ticker portfolio makes exactly 2 external calls, verified in both a unit test and a live run against the real app.

**Q5: A guessed/enumerated holding id belonging to another user is sent to `PUT /api/portfolio/holdings/:id`. Trace exactly what happens and why.**
A: `portfolio.controller.js` first validates the id is a well-formed Mongo ObjectId (400 if not), then calls `portfolioService.updateHolding(req.userId, id, updates)`. The service runs `Holding.findOneAndUpdate({_id: holdingId, userId: req.userId}, ...)` — the ownership check is part of the query itself, not a separate step, so a real holding owned by a different user simply doesn't match the filter and the query returns `null`, exactly as if the id didn't exist at all. The service throws `HoldingNotFoundError` (404), giving the caller no signal about whether the id was invalid or just not theirs.

## 14. Finance interview questions

**Q1: Why is averaging each holding's individual return % the wrong way to compute portfolio return?**
A: It ignores position size. A $100 position at +100% and a $10,000 position at −1% average to +49.5%, suggesting a strong win, but the portfolio's actual dollar-weighted return is close to breakeven — the large position's small loss in dollar terms dwarfs the tiny position's percentage gain. Summing dollar values first (`ΣcurrentValue − ΣcostBasis) / ΣcostBasis`) automatically weights each holding by its actual size (`PortfolioReturn.md`).

**Q2: A holding has a $0 purchase price. What should its return percentage show, and why?**
A: `null`, not `Infinity`. The math (`(currentValue − 0) / 0`) is undefined, and returning `Infinity` would be worse than an honest "undefined" — it could poison any downstream aggregation. Athena's `calculateReturnPercent` explicitly guards a zero cost basis and returns `null`, which the frontend renders as `—` (`UnrealizedGainLoss.md`, `CostBasis.md`).

**Q3: Why does Athena exclude a holding with an unavailable current price from portfolio totals, rather than treating its value as $0?**
A: Because "unknown" and "worthless" are different facts, and conflating them would report a portfolio-level loss the user never actually took. The holding's cost basis is reported separately (`unpricedHoldings`) rather than either silently dropped or silently zeroed against the total.

**Q4: Two AAPL lots bought at different prices are both in a user's portfolio. How does Athena decide "AAPL's return"?**
A: It doesn't compute one lot's return as "the" answer — `groupByTicker()` sums both lots' shares and cost basis into one net position, computes that position's current value from the combined share count, and derives return from the *position's* totals, not either individual lot's. Verified live: two AAPL lots individually returning +101.5% and +0.75% netted to a single +51.1% position return (`PortfolioWeight.md`).

**Q5: What does "42% concentration in one holding" actually measure, and what does it not measure?**
A: It measures that one company's current market value is 42% of the portfolio's total current value — a pure dollar-weighted measure. It says nothing about correlation, sector overlap, or diversification quality beyond raw position size — five holdings at 20% each that are all the same sector would show low top-holding concentration while still being poorly diversified in a way this metric can't see (`ConcentrationRisk.md`).

**Q6: Why does Portfolio Weight use current value instead of cost basis?**
A: Weight answers "how exposed am I to this company right now," which is a function of what the position is worth today, not what was originally paid. A stock that's tripled since purchase represents far more of the portfolio's actual value at risk than its cost basis alone would suggest (`PortfolioWeight.md`).

**Q7: Is Athena's Portfolio Return % the same as an annualized (CAGR-style) return?**
A: No — it's a simple point-in-time calculation with no time dimension. A position held one day and one held five years both just show their raw return since purchase; two portfolios with identical dollar gains but very different holding periods would show the same Portfolio Return %, which is a documented limitation, not an oversight (`PortfolioReturn.md`).

**Q8: Why does Athena's Watchlist show a DCF value using "illustrative" assumptions instead of the same rigor as the interactive DCF tool?**
A: Because a real DCF requires user-specific inputs (beta, cost of debt) the interactive tool correctly refuses to default (`CostOfDebt.md`), and a casual watchlist glance can't reasonably prompt the user for those on every row. Athena reuses the exact same illustrative-default pattern Sprint 8's AI reports already established (`ILLUSTRATIVE_CREDIT_SPREAD`), clearly labeled as illustrative rather than presented with the confidence of a user-directed DCF run.

**Q9: What's the difference between Watchlist's "1Y Return" and Portfolio's "Return %"?**
A: Watchlist's 1Y Return is the stock's own market performance over the trailing year, independent of whether or when the user ever bought it — it's a research statistic. Portfolio's Return % is specific to the user's actual cost basis and purchase date, and only exists because they own shares — conflating the two is exactly the mistake `WatchlistVsPortfolio.md` warns against.

**Q10: A user's watchlist insight says "Financial Health Score changed from 82 to 89." What is that metric actually measuring, and why was it chosen as one of Athena's five tracked change-detection signals?**
A: The Financial Health Score is a composite 0–100 figure combining profitability, liquidity, solvency, cash flow, and growth (`FinancialHealthScore.md`). It was chosen for change detection specifically because it captures multi-dimensional fundamental change in one comparable number, letting a watchlist flag "the underlying business changed" without re-deriving and re-displaying ten raw ratios on every check-in (`watchlistInsights.service.js`'s documented metric-selection rationale).
